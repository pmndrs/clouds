# Audit and reset plan — 2026-10-08

This document supersedes the phase/gate plans (`implementation-plan.md`,
`next-milestones.md`, `implementation-work-queue.md`, `agent-orchestration.md`,
`human-review.md`). Those files are kept for history only.

## TL;DR

The code is healthy (typecheck clean, 129/129 unit tests pass), but the project
optimized for the wrong thing. Six "phases" built a platform (packaging, React
bindings, upscaler adapter, consumer checks, evidence exporters, ~60k words of
docs) around a **correctness reference integrator** that was never designed to be
realtime and never got the core Nubis renderer structure. The result: demos that
bake for seconds on every slider change, march 512 steps per pixel, have a static
noise pattern, hard-coded light colors, and live in a box.

The fix is not more gates. Build what Schneider actually shipped in Nubis³ /
Burning Shores, and build it realtime from day one:
- a (profile, detail type, density scale) voxel field plus an SDF
- density created at runtime by noise up-rez
- an SDF sphere-trace march
- a voxel light grid with profile-based inner glow and ambient
- a near/far resolution split

Develop it on Guerrilla's own released cloudscapes (the Nubis Voxel Cloud Pack).
Then add sky coverage, GPU-generated cloudscapes and VDB-authored clouds as
further sources of the same field. Tidewater/Sky Pro, built on the decade-old
HZD recipe, is the visual and performance bar, not the code base.

### Why the demos "bake hard" (concrete)

From `examples/lab/realism/main.ts` and `packages/three/src/volumetric/`:

- Default **512 view steps + 128 light steps** per pixel, uniformly spaced across the
  box chord (`realistic-shader.ts`, the `for(i<steps)` loop). No coarse/fine
  stepping, no empty-space skip (the occupancy mask is not even bound in realistic
  mode), no cone-proportional step growth.
- Any sun/coverage/scale change rebakes a ≤192³ optical-depth volume where **every
  voxel marches 128 steps through the full procedural density** (~900M density
  evaluations) before the next frame.
- The frame loop only renders when "dirty"; there is no wind/time animation.
- Jitter is a fixed per-pixel hash with an explicit comment refusing to use a frame
  seed because "this experiment does not rely on unimplemented history".
- Noise textures are built on the CPU in JS (`createMorphologyNoise`).
- Lighting is decoupled from the sky: `ambient=mix(vec3(.025,.04,.065),vec3(.15,.22,.32),h)`
  and `sun=vec3(6.0,5.7,5.1)` are constants; no transmittance LUT, no aerial perspective.
- Domain is a finite box with a 180 m fade at the sides, not a planetary shell.

### How it went off track (decision trail)

Schneider's work is cumulative. HZD 2015/2017 established a core:
- noise erosion of a coarse shape
- the lighting model (Beer/powder/phase/multi-scatter/ambient)
- quarter-res temporal rendering
- weather maps as authoring input

Nubis Evolved and Nubis³ kept all of that. What changed was where the coarse
shape comes from (a voxel field of profile/type/density scale plus an SDF) and
how the march skips empty space. The project took a different path:

1. **2026-09-16, `approach-decision.md`.** "Classic procedural vs voxel-first"
   was framed as an either/or. The doc then says: "Do not require shipping the
   complete classic system before trying the voxel approach." That skipped the
   HZD core, which is the part that makes clouds look like clouds. The "small
   classic procedural reference for comparison" it promised was never built.
2. **Same day, `library-spec.md:49` and decisions D04/D05.** The central
   interface became a *density source* that the renderer samples ("density
   sampling + occupancy/majorant"), with a dense density texture first. Nubis³
   needs the opposite. The source supplies a shape description and the renderer
   creates density by erosion. Every later source (ellipsoid atlas, morphology
   field, VDB r8) baked final density to fit that interface.
3. **2026-09-17, P1.** The first renderer was a "voxel reference renderer": a
   correctness integrator with uniform steps, no history and a bounded box. It
   was never replaced. Every later phase iterated on it.
4. **P0–P4 were all committed within 2 days.** Integration lab, cloudscape,
   lighting, and FSR reconstruction comparisons. Each phase added evidence docs
   and review gates while the image was labelled "provisional".
5. **Most of the question/answer rounds were about library integration:** R3F
   v10, sky envmap policy, shadows, packaging, `pmndrs/clouds`. So the plan
   shaped itself as a library platform. "The point of voxels is to work inside,
   so that should be our tests/showcases" sent the first showcases into isolated
   volumes rather than a sky.
6. **2026-10-08 directive (`project-status.md`).** "Complete the platform
   through P6, then advance realism." Platform work went first again.
7. **The quality problem was misdiagnosed.** When the realism lab looked smooth,
   the response was more shape sources: Houdini particle VDBs, morphology
   studies. Candidates were scored against brute-force or path-traced references.
   The real gaps were lighting, temporal sampling and the data model.

The research itself was mostly accurate (the slide citations are correct). What
went wrong was translating it into an architecture, and the order of work.

### Root causes

1. **Platform before picture.** P4 (upscalers), P5 (React/API), P6 (packaging,
   consumer checks) were built while the core image was explicitly "provisional".
2. **Reference-first instead of realtime-first.** The "correctness reference"
   architecture (bounded volume, uniform quadrature, no history) was iterated on
   for realism instead of being replaced by the standard realtime structure.
3. **Process overhead.** Evidence JSON, GPU "checks", review gates, model-routing
   docs. 60k words of docs against ~6.5k lines of library code. Agents spent their
   budget proving correctness of things that didn't matter visually.
4. **Wrong root for quality problems.** Large effort chased shape (Houdini
   particle VDBs, ellipsoid lobes, morphology studies) when the bigger visual gaps
   were lighting, sky coupling, and sampling.
5. **Wrong Nubis³ data model.** The research notes read the Nubis³ slides
   correctly but the code bakes *final density* (r8 atlas tiles, r8 VDB volumes).
   Nubis³ stores a *shape description*: dimensional profile, detail type,
   density scale, plus a separate SDF. Density is created at runtime by eroding
   the profile with tiling noise. Baked density can't get crisp detail
   at any distance, which is why the VDB fixtures look like smooth blobs.
6. **Acceptance bar set by a brute-force reference.** `cloud-quality-bench.md`
   judged candidates against a 640-view/64-light-sample reference and a Cycles
   8-bounce render, rejected noise mips because they scored worse against it, and
   blocked performance work behind image quality. Production renderers never
   converge; they hide error with jitter, mips and temporal accumulation.
7. **Production cloudscape shader is weaker than the "realism" lab:** single HG
   lobe (g=0.45), flat ambient, no powder or multi-scatter, a sine-product detail
   term instead of Worley erosion (`cloudscape/shaders.ts:214`), 48 uniform light
   samples across the whole world box, up to 320 full-res view steps.
8. **Work left uncommitted.** 177 files were only in the working tree until
   `066768f`.

## 2. What "good" looks like — reference implementations

**Source of truth for the code:** Schneider's own material, in order:
- HZD 2015/2017
- Nubis Evolved 2022
- Nubis³ 2023
- "Synthesizing Realistic Clouds for Video Games"

The decks live in `artifacts/research/` (gitignored, copyrighted). Our
implementation notes are in `docs/research/nubis-sources.md`.

**Tidewater / Sky Pro are the visual and performance bar, not the code
baseline.** They show what a browser can hit. Their simplifications do not
match the target architecture:
- one 64³ texture serves both shape and erosion
- no curl noise
- no cloud types
- no voxel/SDF
- no fly-through

Use them for side-by-side captures and frame-time comparison.

For comparison, the HZD-era realtime structure Tidewater uses:

- Shape + detail noise and blue noise **loaded or GPU-baked once**.
- Weather map (1024²) + max-reduced 64² "bounds" grid for empty-space skipping,
  regenerated only when weather changes.
- **Trace 1 of every 16 pixels per frame** (4×4 lattice) at half res, with blue-noise
  + golden-ratio temporal jitter.
- Adaptive march: coarse 4× steps on a cheap density, step back and refine on hit,
  drop back to coarse after 4 empty steps; step size ∝ pixel cone; stop at T < 0.003.
- Light: 6 cone taps growing 1.7× per tap to ~2.5 km with per-tap mip LOD; reuse
  light result across ~3 view steps; cheap light once opacity > 0.5.
- Energy: dual-lobe HG (0.8 fwd / 0.2 back) with 3 octaves halving g;
  powder faded toward the sun; ambient from sky-view LUT zenith/horizon with two
  upward visibility probes + ground bounce; sun from the transmittance LUT.
- Resolve: depth- and alpha-weighted upsample, Catmull-Rom history, neighborhood
  clamp, wind-compensated reprojection; history reset on cuts/sun/coverage.
- Amortized side products: 256² cloud shadow map (¼ rows/frame), sky panorama
  (1/16 texels/frame).

Tidewater's realtime structure is the HZD-era recipe:
- a weather map plus a bounds grid
- a 1-in-16-pixel trace with temporal resolve
- coarse/fine adaptive steps
- a 6-tap cone light march
- powder and multi-scatter octaves

It is good evidence of what a browser can afford. Parts of it are reusable for
our vertical-profile sky layer (section 3). **The voxel path follows Nubis³
instead:**
- SDF sphere tracing
- a voxel light grid
- profile-based inner glow and ambient instead of powder
- a near/far resolution split instead of temporal history for near clouds

## 3. Target architecture

Mirror the Nubis³ family. Every source produces the same triple,
**(dimensional profile, detail type, density scale)**. One shared up-rez,
lighting model and march consume it. Formulas, constants and slide citations
are in [`research/nubis-sources.md`](research/nubis-sources.md).

```
 sources → (profile, type, scale) NVDF + SDF                 shared runtime
 ┌─────────────────────────────────────────────┐   ┌──────────────────────────────────────────┐
 │ Voxel: official Nubis pack NVDFs            │   │ up-rez: Alligator/Curly-Alligator noise, │
 │ Voxel: authored VDB/mesh → NVDF converter   │──▶│   wispy↔billowy by type, erosion, HHF    │
 │ Voxel: GPU-generated from weather (+evolve) │   │ march: SDF sphere trace + sqrt(d)·0.08   │
 │ 2.5D: envelope / vertical profile (sky)     │   │ light: 2 near samples + light grid (τ↑,τ☀)│
 └─────────────────────────────────────────────┘   │ ms inner glow, ambient, HG lobes, sky LUT│
                                                   │ near<200m @ ¼ res, far @ ½ res, compose  │
                                                   └──────────────────────────────────────────┘
```

- **Voxel path (primary):**
  - One dense NVDF grid per cloudscape region (512×512×64 at 8 m). Start with
    `rgba8unorm`, about 67 MB uncompressed, and move to BC later.
  - A separate `r16` SDF.
  - Up-rez noise is evaluated per sample. Density is never baked.
- **Light grid:**
  - 256×256×32 summed density toward the sun and toward the sky.
  - Built in compute and amortized over 8 frames. A sun or time-of-day change
    costs no frame stall.
- **Vertical-profile sky layer:**
  - The same up-rez and lighting, driven by 2D weather fields, for the
    unreachable sky and horizon.
  - This is where temporal amortization belongs (Nubis uses 16 frames).
- **Authored clouds:** VDB or mesh → SDF → profile, plus painted or derived
  detail type and density scale, composited into the region NVDF (Atlas-style).
  Artist shapes get Nubis detail for free. This is the Sea of Thieves goal,
  done the Nubis way.
- **Integration:** raw WGSL compute on three's device through the existing
  `gpu/` interop. Sky and aerial perspective come from @pmndrs/sky LUTs.

## 4. Plan

Each milestone ends with three things:
- a flagship demo with a continuous animation loop
- an always-on GPU timing HUD per pass
- side-by-side captures at fixed cameras against Tidewater, plus the Nubis
  slides where the official cloudscapes allow a like-for-like shot

Commit at every working step.

### M0 — Reset and source data (1–2 days)

- Move the old labs under `examples/legacy/`. Archive the gate/evidence docs.
- **Get the official Nubis Voxel Cloud Pack** (110 MB) once the user approves
  the download. Check its license, then convert its TGA/VDB NVDFs and noise
  into GPU-ready files with a small Node or Python tool.
- New `examples/sky/` flagship page: three WebGPURenderer, @pmndrs/sky,
  ground, free-fly and orbit camera, time of day, wind, timing HUD.
- Capture Tidewater at 4 fixed cameras for the visual bar.

### M1 — Nubis³ voxel renderer on official data (2 weeks) ← the important one

1. Load the Parkouring and Stormbird NVDFs and the SDF, or generate the SDF
   with a GPU jump flood if the pack lacks one.
2. Load the official noise (Alligator / Curly-Alligator RGBA 128³, with mips).
   Use a GPU port of the generator only if the license blocks redistribution.
3. Up-rez density exactly as in `nubis-sources.md` §3, including the early-out
   and the near-camera HHF detail.
4. SDF sphere-trace march with `max(sdf, max(1, sqrt(t)·0.08))`. Jitter is
   animated under 250 m and static beyond.
5. Lighting:
   - two in-march light samples plus a 256×256×32 summed-density grid (sun and
     sky), amortized over 8 frames
   - ms inner-glow term
   - ambient `pow(1−P, .5)·exp(−τ↑)`
   - HG lobes
   - sun and sky color from atmosphere LUTs
6. Near/far split: under 200 m at quarter res, over 200 m at half res, then a
   depth-aware upsample and composite with aerial perspective.
7. Cloud shadow onto the ground, from the light grid.

**Done when:**
- You can fly through the Stormbird cloud and around Parkouring at frame rate,
  with inner glow, dark edges and silver lining all visible.
- Clouds take ≤ 4 ms on the M5 Pro at 1440p output.
- Sun changes never stall.
- It looks at least as good as Tidewater from the ground.

### M2 — Sky coverage and our own cloudscapes (2 weeks)

1. A vertical-profile 2.5D layer for the distant and unreachable sky, sharing
   the up-rez and lighting. It uses 16-frame temporal amortization and blends
   seamlessly into the voxel region.
2. GPU NVDF generation from weather and type maps: profile, type and scale
   written by compute, SDF by jump flood. This gives procedural voxel
   cloudscapes anywhere, not only shipped data.
3. A region system: the camera-centred NVDF window streams or regenerates as
   you travel.

**Done when:** a 40 s ground → through-cloud → above-layer flight over a
generated cloudscape, with distant sky coverage at the horizon and no seams or
popping.

### M3 — Authored clouds (1–2 weeks)

1. VDB/mesh → NVDF converter:
   - SDF from the iso-surface, or from the density threshold for fog VDBs
   - profile from the SDF, the way Nubis does it
   - detail type from a VDB attribute or a height heuristic (wispy undersides)
   - density scale from the source

   Reuse the Houdini bridge (`voxelRangeAsFloat`). Houdini and Blender are
   optional authoring front ends, not runtime requirements.
2. Composite authored clouds into the region NVDF with a transform (cutout,
   squash, blend modes, as in Atlas). Optionally add a per-instance bounded
   NVDF for movable hero clouds.
3. Drag a `.vdb`-derived file into the flagship demo and place it in the sky.

**Done when:** an artist VDB placed among procedural clouds shows the same
wispy/billowy detail and lighting as its neighbours.

### M4 — Beyond Nubis³ (Schneider's stated future work)

- **Realtime cloud evolution with on-the-fly SDF regeneration.** This is
  Schneider's open item, and WebGPU compute makes it reachable for us.
- Phase modulated by the in-scatter probability field.
- Baking lighting functions into LUTs.
- Sparse NVDF storage for larger worlds.
- BC-compressed NVDF and SDF.
- Lightning in storm cells.
- Optional temporal accumulation for near clouds on weaker GPUs (web budgets
  differ from PS5's).

### M5 — Library and React

Rebind `@clouds/three` and `@clouds/react` to the new renderer. Define the
public API from what the flagship demo actually needed, then publish.

## 5. Working rules for agents going forward

- **Image first.** No platform/API/packaging work before M1 is done.
- **Frame rate is a hard constraint, not a preset.** Anything that stalls a frame
  is a bug.
- **Always animated.** The demo loop renders every frame with wind and history.
- **Commit every working step** to a branch; never leave work only in the tree.
- **Docs budget:** one status section in this file per milestone, plus research
  notes. No evidence JSON, review-gate docs, or orchestration docs.
- **Comparison over self-reported checks:** side-by-side captures vs Tidewater
  and the Nubis slides are the acceptance test. Never use a brute-force or
  path-traced render as the quality gate. Quality and budget are designed
  together.
- Schneider's talks are the code reference. Tidewater (MIT) is a visual/perf
  comparison, not a code baseline; the threejsskypro.com bundle may not be copied.
