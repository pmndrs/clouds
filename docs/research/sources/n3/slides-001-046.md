# Nubis Cubed, slides 1–46: a brief (Nubis-centric) history of cloud rendering
Source: Schneider, *Nubis Cubed*, SIGGRAPH 2023 Advances (`artifacts/research/nubis/Nubis Cubed - 4k.pptx`, id `n3`).
Slide numbers are pptx presentation order. PDF-with-notes pages for this range are p001–p054 (not a fixed offset: s18 = p019,
s24 = p025–026, s28 = p030–031, s36 = p042, s45 = p052, s46 = p053–054).
Tags: shape detail light perf · Range status: 🟦 note written, 🟩 code transcribed (7 slide listings + 1 assembled file).

## In one paragraph
This range is the recap of the 2.5D system that shipped in Horizon Zero Dawn and Forbidden West, compressed from NE 2022
(Nubis Evolved). Almost every formula here is already in `hzd-nubis-evolved.md` and `sources/ne22.md`; N3 adds no new maths
for the 2.5D model. What N3 adds: (1) the two vertical-profile lookup tables as **full-resolution 64×64 images** on s18
(`media/image32.png`, `image33.png`), which can be sampled numerically (done, below); (2) side-by-side posters of the
**un-eroded dimensional profile and the eroded result** for both methods (s17/s21/s24), the clearest picture in any Nubis
deck of what "noise erodes a low-res profile" means; (3) the cheap lighting terms stated as one equation
(`Light = Direct + Ambient + Secondary`, `Direct = T·phase1 + MS·phase2`) with the MS reasoning in the notes; (4) timings and a
pros/cons table (s46) that explains why Guerrilla moved to voxels. For our procedural model the useful parts are the
**top/bottom type tables**, the **erosion law** `saturate(noise − (1 − profile))`, the **type-driven wispy/billowy blend**,
and the **ambient = sqrt(1 − profile)** term.

## Slide by slide
Trivial / video-only, grouped: **s1** (title, studio logo in puffs; notes: 6th SIGGRAPH cloud talk since 2011), **s2** (title;
"cube Nubis" framing; video), **s3** (Rio 2011: fluid-sim "voxel clouds" assembled into "Frankencloudscapes", 10 min to 4 h per
1080p frame on one core), **s4** (joined Horizon 2014 to replace Killzone's 2D skybox; video), **s5** (Houdini voxel cloud with
velocity streamlines), **s7** (Aero video: cloud growth only, not combustion), **s8** (2014 tests: RGB billboards and a voxel
skybox; too slow for PS4, shelved), **s9** ("2.5D Clouds, est. 2015": 3D clouds stored as 2D textures), **s10** (bibliography:
HZD 2015, 2016 talk, N17, NE 2022).

- **s6** Aero solver micro-solver order for one frame: Sourcing → Apply Buoyant Force → Non-Divergence → Advect Velocity →
  Advect Density (diagram lists them bottom to top; read order uncertain). Relevant only to the voxel library (L2), not procedural.
- **s11** What made 2.5D Nubis work: compress cloudscapes, add cloud-specific density and lighting detail at render time,
  fine-tuned ray march. Cost **0.2 to 5 ms** (far view vs flying through). Poster `image21`: orographic fog wrapping snowy peaks
  (good envelope-method reference).
- **s12–13** Ray-march procedure: for each pixel, march between the layer's top and bottom; per step sample density, sample light
  (a second, expensive march to the sun), integrate, choose next step; stop at full opacity. Generic; same as NE.
- **s14** Two methods reviewed: **Vertical Profile** for high tropospheric clouds out of reach, **Envelope** for orographic
  clouds the player flies through. Diagram (p014) places them: envelope layer hugs terrain below the peaks, vertical-profile
  shell above. Shape figure: yes (layering diagram).
- **s15–16** NDFs = 2D "Nubis Data Fields" the compute shader uses to "decompress" 3D clouds; mapped over a **16 km × 16 km**
  area of the world (s16). Same as NE.
- **s17** Both methods build a high-res 3D volume from a **low-res dimensional profile**; the profiles look alike but are built
  differently. Posters (in s17, s21, s24): `image28` vertical-profile profile alone (smooth stacked lobes with soft shelves),
  `image29` envelope profile alone (a smooth flat-bottomed dome blob), `image30` envelope eroded, `image31` vertical-profile
  eroded (cumulus field). **Shape figure: the best one in the range** (before/after erosion for both methods).
- **s18** Vertical Profile Method: **5 NDFs** (min height, max height, coverage, bottom type, top type). Min/max set the vertical
  range; top and bottom type each index a lookup texture; the two lookups are multiplied into `vertical_profile`; then
  `dimensional_profile = vertical_profile * cloud_coverage`. LUT images sampled numerically: see "Profile tables" below.
  Shape figure: yes (the tables).
- **s19** Envelope Method: **4 NDFs** (min height, max height, type, density). Profile = bottom × top × edge gradients. Diagram:
  a dome of clouds sitting on a flat "cloud min height" line under an arc at "cloud max height". Shape figure: yes.
- **s20** "Bonus slide", the envelope code (n3-s020.hlsl): `h = remap(height, min, max, 0, 1)`, `top = pow(1 − h, 1.5)`,
  `bottom = pow(h, 2.0)`, `edge = remap(sample_height, 0, 35, 1, 0)`. Same as NE p.97. `sample_height` is not defined; the
  notes only say the edge gradient rises "going in from the sides", so it is probably a distance (m) to the envelope's side.
  Unverified. Note top × bottom peaks at h = 4/7 ≈ 0.571 with value (4/7)^2 (3/7)^1.5 ≈ 0.091: the raw product is small, so it
  must be renormalised or scaled by the density NDF; N3 does not say how (see NE p.105 for the 0.27-power sharpening).
- **s21** 3D noise erodes the profile and "up-rezzes" it (same posters as s17).
- **s22** Nubis noise (HZD era): **4 channels, 128³, uncompressed, 2 bytes per texel, 4.194 MB** (= 128³ × 2 B, so about 4 bits per
  channel). Channels: low-freq "Perlin-Worley", low-, medium-, high-freq Worley. Perlin-Worley gives a wispy/billowy mix; Worley
  gives billows. Combined **per model** into a "wispy noise composite" and a "billowy noise composite" (recipe not shown in N3).
  Thumbnails `image34`–`image40` (two sets overlaid at the same positions: 256 px png and 128 px jpg; which set is the composite
  is not clear). Shape figure: yes (channel thumbnails).
- **s23** Blend wispy → billowy by the **Type** NDF: `noise_composite = lerp(wispy_noise, billowy_noise, detail_type)`. The code
  comment says "blend to wispy as the density scale decreases", which does not match the code's `detail_type` weight; the notes say
  Type. Gradient bar: type 0 = wispy, 1 = billowy.
- **s24** Erosion: `cloud_density = saturate(noise − (1.0 − dimensional_profile))`, "subtraction of the inverse of the profile
  from the noise composite". Same as NE p.34. Note the polarity: **high noise = more cloud** (noise is added to the profile and
  the sum thresholded at 1), unlike the voxel-era `ValueErosion(profile, noise)` where high noise removes cloud.
- **s25** "Pseudomotion": `noise_sample_pos = sample_pos − wind_direction * scroll_offset` for both methods. Stills `image41`
  (vertical-profile cumulus field, sun) and `image42` (envelope cloud at dusk).
- **s26–27** `Light Energy = Direct Scattering + Ambient Scattering + Secondary Scattering`: sun; sky and neighbouring clouds;
  sources such as lightning. Each method computes them slightly differently (pointer to NE 2022).
- **s28** `Direct Scattering = (Transmittance * Primary Scattering Phase) + (Multiple Scattering * Secondary Scattering Phase)`.
  Notes, paraphrased: transmittance comes from Beer–Lambert on optical depth gathered by the expensive light march; phase is
  "several" HG lobes for an art-directable, somewhat physical forward bias; **MS uses the dimensional profile as a probability
  field** (deeper = more scattered photons), **attenuated by a second Beer–Lambert curve** (MS light is itself absorbed),
  **attenuated over height** (less light enters from below), then **scaled by its own phase function** so it stays directional.
  No constants on the slide. The Beer graph (`image43`) plots T = exp(−5 d) for d in 0..1 (measured from the curve: k = 4.94–5.04);
  illustrative only.
- **s29** Same cloud field without / with the MS approximation (`image44`, `image45`; by appearance `image45` is the darker,
  no-MS one; unverified).
- **s30** Ambient: `ambient_scattering = pow(1.0 − dimensional_profile, 0.5)`. Reasoning: sky light comes from above and around
  and penetrates only the surface; the profile already runs from outside (0) to inside (1), so its inverse is the probability that
  ambient light reaches a point and scatters to the eye. No height term on this slide.
- **s31** Ambient only / direct only / both (`image46`–`48`; by appearance 48 is ambient only, 47 direct only, 46 both).
  Useful to judge how much of the look is ambient.
- **s32–33** Secondary (lightning) light: a third march per sample would be needed; instead a **modelled volume of light** around
  the source gives the energy at each primary-march sample (diagram p039: red sphere with falloff, samples along the view ray).
  Details deferred to the voxel section (s130 in N3).
- **s34** Superstorm (HFW) with red lighting and lightning (video; poster `image54`).
- **s35–36** Vertical-profile **adaptive step**: `step = 3.0 + 60.0 * distance / 16384.0` (m): 3 m at the camera, 63 m at
  16.4 km (+3.66 m per km). Same as NE p.39.
- **s37** Vertical-profile cost **0.5 ms** (partial sky) to **2.2 ms** (full sky). Posters `image55` (pink cumulus at sunset from
  a flying mount) and `image56` (sun rays through broken puffs). Good reference renders of the HZD floor.
- **s38–39** Envelope march: **cone step mapping** (Dummer 2006) + **distance step mapping**, using height data only: intersect
  the ray with cones built from the height field to find the largest safe step; distance steps cap the sample count outside
  the cones and clouds; inside the envelope switch to small steps and real density (diagram p046).
- **s40** Sample distribution debug (`image58`): red dots cluster around clouds in valleys, sparse in empty space.
- **s41–42** Envelope scene **4.2 ms before, 1.3 ms after** the cone/distance stepping (same frame, GPU profiler visible).
- **s43–44** Vertical-profile **temporal upscaling over 16 frames**: a 20 ms render becomes 2 ms; fine for distant clouds, fails
  near the camera because the image cannot resolve under fast motion (diagram: 4×4 pixel dot grid).
- **s45** Envelope clouds instead render **two passes split at 200 m**: near at **480×270** (expensive, low res), far at
  **960×540** (to avoid aliasing). The slide's axis labels swap width and height (960 px drawn vertically); read as 960×540.
- **s46** Comparison table (vertical profile / envelope): evolution yes / pseudomotion only; time of day yes / yes; lightning
  yes / no; high frame rates yes / yes; flight-capable no / yes; freeform modelling no / no. Notes: envelope could not evolve
  because cones and distance fields could not be rebuilt on the fly; neither method is intuitive to author; goal from art
  director JB: flight through "proper clouds" → the voxel prototype.

## Profile tables (s18), sampled from the slide images
Files: `extracted/n3/data/n3-s018-lut-top-type.csv`, `...-bottom-type.csv` (64×64, row 0 = bottom). Both images are 64×64 cells
and are drawn **flipped vertically** on the slide (`flipV` in slide18.xml), so the sampling flips them back to the displayed
orientation (height up, type right). The bottom table is a 15-colour palette PNG (values ±0.04); an `hdphoto3.wdp` original
exists but was not decoded.
- Both tables share a **floor at row 16–18 (h ≈ 0.27)**: below it top = 1 and bottom = 0, so the product is 0. The cloud occupies
  h ≈ 0.27..1 of the table. (Whether min height maps to h = 0 or to the floor is not stated.)
- **Top type** (value per height; columns type 0, 0.25, 0.5, 0.75, 1.0):
  `h .29: 0 .90 .97 .98 .98 | .38: 0 .64 .89 .93 .94 | .48: 0 .37 .84 .85 .75 | .57: 0 0 .65 .67 .76 | .67: 0 0 .58 .76 .80 |
  .76: 0 0 .63 .69 .62 | .86: 0 0 .39 .51 .53 | .95: 0 0 0 .35 .40`.
  Top extent (last row > 0.05): type 0 → 0.27 (a one-row sheet), 0.13 → 0.41, 0.25 → 0.54, 0.38 → 0.63, 0.5 → 0.87, 0.63 → 0.91,
  0.76 → 0.96, ≥ 0.89 → 0.98. The column top rises **in steps**, and high types are **not monotone**: a dip around h 0.5–0.6 and a
  second shoulder at 0.65–0.7 (tiered tops), then a long taper to about 0.4 near the top (soft, erodible heads).
- **Bottom type**: type 0 ramps 0.33 → 0.67 → 0.80 within 0.1 of the floor (crisp base), then 0.8–0.91; type 1 ramps slowly:
  0.2 at +0.06, 0.4 at +0.16, 0.5 at +0.28, 0.8 at +0.54 (a long soft underside). Max anywhere ≈ 0.91, so `vertical_profile`
  never reaches 1.
- With the s24 erosion, a slow bottom ramp means only noise peaks survive low down: **bottom type 1 should read as the ragged,
  wispy base** and type 0 as the flat one. `ne22.md` (line 31) reports NE p.27's render "bottom type 0: ragged underside"; this
  is the opposite reading. **Resolved by the lead (n3.md §7a): type 0 = crisp, flat base.** NE p.26's table has the same
  orientation (left column bright right down to the floor, right column a long dark fade), and the NE p.27 still labelled
  "Bottom Type = 0.0" shows flat, smooth undersides on the main masses; the ragged bits are distant fringe.

## Contradictions and corrections to existing notes
- `ne22.md:31` reads NE p.27 as "bottom type 0: ragged underside"; the s18 table numbers suggest type 0 is the crisp base (see above).
- `nubis-sources.md:68` (N3 s89–90 voxel noise) calls the noise "RGBA16, 4.2 MB". 4.194 MB for 128³ is 2 bytes per texel total
  (s22 says so explicitly for the HZD noise), so "RGBA16" must mean 16 bits per texel, not 16 bits per channel. s90 repeats the
  same label block verbatim. The pack's noise TGAs use the full 8 bits per channel (lead's check, n3.md §7b), so the shipped
  data is RGBA8 (8.4 MB) and the slide label is best treated as a reused, wrong caption.
- The s23 code comment ("as the density scale decreases") disagrees with its own code (weight = `detail_type`). Trust the code.
