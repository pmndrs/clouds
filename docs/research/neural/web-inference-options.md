# Running a HaloRT-sized network in the browser on WebGPU (state as of 2026-11-23)

Facts only, no recommendation. Each claim carries a source. "Unverified" = from memory or a secondary summary, not a primary doc. The workload: ~1.2M-parameter U-Net + HaloNet local attention, 8 input channels, 1 output, run 6x/frame, 512^2-2048^2.

## 0. Platform baseline

- WebGPU shipped in Chromium (Win/Mac/ChromeOS v113; Android v121; Linux Intel Gen12+ v144, NVIDIA/Wayland v147), Firefox (Windows v141, Apple-silicon macOS v145, all macOS v147; Linux nightly only), Safari 26 (macOS/iOS/iPadOS/visionOS, default on). Source: https://github.com/gpuweb/gpuweb/wiki/Implementation-Status
- Chrome WebGPU news index: subgroups for ML (Chrome 134), subgroup size control (151-152), `maxTextureArrayLayers` raised (126), `maxStorageBuffersPerShaderStage` up to 16 and `maxSampledTexturesPerShaderStage` up to 48 (Dawn updates in the 146 post), f16 on Linux/NVIDIA (155-156), WGSL `linear_indexing` (147-148), `buffer_view` extension (153-154). https://developer.chrome.com/docs/web-platform/webgpu/news and https://developer.chrome.com/blog/new-in-webgpu-146
- Caniuse: Firefox subgroups not supported through v156 (secondary, search-result snippet): https://caniuse.com/wf-webgpu-subgroups
- Limits worth checking at runtime (spec defaults, unverified here): maxColorAttachments 8 (with a 32-byte per-sample budget), maxTextureArrayLayers 256, maxStorageBufferBindingSize 128 MiB, maxBufferSize 256 MiB, maxComputeInvocationsPerWorkgroup 256. Query `adapter.limits` for real values.
- Per-dispatch overhead measured 2026: ~24-58 us on CNN/ViT/U-Net-style dispatch streams (single-author arXiv study, mostly LLM focus): https://arxiv.org/abs/2604.02344. At 6 nets x (tens of layers) x several dispatches, dispatch count matters at 60 fps.

## (a) ONNX Runtime Web, WebGPU execution provider

- **Version**: npm `onnxruntime-web` 1.30.0 exists (notes cover changes since 1.29.1; date not shown, "2 months ago" on the aggregator): https://newreleases.io/project/npm/onnxruntime-web/release/1.30.0 . 1.27.0/1.27.1 and 1.26.0 are also listed. WebGPU import: `import * as ort from 'onnxruntime-web/webgpu'`; `executionProviders: ['webgpu']`. Docs recommend `onnxruntime-web@dev` for newest features: https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html
- **1.30.0 WebGPU items**: conv fusion for eight more activations, GELU/LayerNorm fusions (LayerNorm fp16 correctness fix), subgroup-matrix MatMul/Gemm, Conv3DNaive fp16, "synchronization fixed for user-provided GPUDevice instances", pipeline-compile workers scale with CPU count.
- **Op coverage** (JSEP/WebGPU kernel registry read from `onnxruntime-web@1.27.0/lib/wasm/jsep/webgpu/op-resolve-rules.ts`, https://cdn.jsdelivr.net/npm/onnxruntime-web@1.27.0/lib/wasm/jsep/webgpu/op-resolve-rules.ts): present: Conv, FusedConv, ConvTranspose, BatchNormalization, InstanceNormalization, LayerNormalization, SkipLayerNormalization, MatMul, Gemm, Einsum, Softmax, Attention, MultiHeadAttention, GroupQueryAttention, Gather, GatherElements, GatherND, ScatterND, GridSample, DepthToSpace, Resize, Pad, Slice, Split, Concat, Transpose, Tile, Expand, Where, Cast, ReduceX, Gelu/FastGelu/QuickGelu, Sigmoid, Relu, LeakyRelu, Elu, pooling ops. Not in the list: `GroupNormalization` (ONNX op; exporters usually decompose to Reshape+InstanceNorm or primitives, so check what `torch.onnx.export` emits), `SpaceToDepth`, `Unfold`/`Im2Col` (no such ONNX op: PyTorch `unfold` exports to Slice/Gather/Reshape chains). Shape ops (Reshape, Squeeze, Flatten) are handled elsewhere in the EP and not shown in that file. A single op missing from the WebGPU EP falls back to WASM/CPU for that node, which creates a CPU<->GPU copy per boundary. HaloNet's halo/windowing and relative-position bias would need to be checked op-by-op against this list when the model is exported.
- **fp16**: model can be fp16 / mixed (the WebGPU EP needs the `shader-f16` adapter feature; doc page itself says nothing on fp16, so how a given fp16 graph is handled is unverified). Chrome has had `shader-f16` since 120. https://developer.chrome.com/blog/new-in-webgpu-120
- **Graph capture**: session option `enableGraphCapture` (WebGPU EP only): static shapes, all kernels on the WebGPU EP; kernels captured on first run and replayed; init fails if unsupported. `freeDimensionOverrides` can fix dynamic dims. https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html
- **IO binding / GPU residency**: `ort.Tensor.fromGpuBuffer(gpuBuffer, {dataType, dims})` for inputs; outputs: `preferredOutputLocation: 'gpu-buffer'` (global or per-output) or pre-allocated output buffers passed in `fetches`; user-created GPU tensors don't own the buffer (you `buffer.destroy()` yourself); model-output GPU tensors are runtime-owned (`dispose()`). Storage buffers only, **not textures**: a render pass output (texture) must first be copied into a buffer (`copyTextureToBuffer`, GPU-to-GPU) and the result copied back to a texture. Source: ep-webgpu tutorial above.
- **Sharing a GPUDevice with three.js**: `ort.env.webgpu.device` can be *set* to a user-created `GPUDevice` ("use at user's own risk"; docs on `powerPreference` say create your own adapter/device and assign it); it can also be *read* after the first session (resolved Promise) to hand ORT's device to another consumer. ORT creates its own device with its own `requiredFeatures/requiredLimits`, so a foreign device lacking them is "not guaranteed to work"; behaviour varied between versions. https://onnxruntime.ai/docs/api/js/interfaces/Env.WebGpuFlags.html (the 1.30 notes list a sync fix for user-provided devices). Whether `three.WebGPURenderer` accepts an externally created device: three's `WebGPURenderer({ device })` parameter exists in recent releases (unverified here, check r187 source). Buffers and textures cannot cross devices, so one device must be common.
- **Typical overhead / timing evidence**: Visionary (arXiv 2512.08478) per-frame ORT WebGPU inference outputs consumed as storage buffers by a WebGPU splat renderer, RTX 4090: 4.8-9.3 ms for small/medium MLP decoders; paper does not state explicitly if the device is shared. `@huggingface/kernels` (Sep 2026) claims 2.57x geometric-mean speedup over ORT WebGPU kernels across 809 cases on Apple M4 (ops listed include MatMul, Softmax, LayerNorm, Einsum; conv/attention not explicitly listed): https://huggingface.co/blog/webgpu-kernels . ORT WebGPU conv speed on this exact U-Net size: no published number found; must be benchmarked.
- ORT also offers `Conv` via im2col/MatMul paths plus subgroup-matrix MatMul (1.30), relevant for Apple/NVIDIA/Intel if the browser exposes it (browser support for subgroup matrix not verified).

## (b) WebNN

- **Status**: still an origin trial, not a stable shipping feature in Chrome/Edge. Origin trial planned for Chrome 146-148, repeatedly delayed by release-blocking issues; re-enabled M-147 through M-149, then disabled again pending a new target milestone; Android excluded (CPU only). Edge trial page marked closed (expiry 2026-08-11). W3C spec at Candidate Recommendation Draft (June 2026, secondary source). Sources: https://mid.mail-archive.com/blink-dev@chromium.org/msg15933.html , https://mid.mail-archive.com/blink-dev@chromium.org/msg15857.html , https://phoronix.com/news/chrome-146-beta . No evidence of Safari or Firefox support (unverified).
- **Backends**: CPU, GPU (DirectML on Windows via Chromium), NPU (device-type options). Backends per OS beyond that: unverified.
- **WebGPU interop**: `MLTensor` created exportable (`createExportableTensor`) then `exportToGPU()` returns a `GPUBuffer` (buffer, not texture). Initial interop spec merged (PR #942, W3C WebML minutes 2026-09-24); v2 work: zero-copy device selection `createContext({ interopDevice: gpuDevice })` (issue #941), which depends on WebGPU multi-adapter and is "not fully fleshed out"; custom export usage flags under discussion (#954). Chromium: `createTensor()` for WebGPU interop was disabled earlier because not fully implemented; prototyped only on some platforms. Sources: https://www.w3.org/2026/09/24-webmachinelearning-minutes.html , https://www.w3.org/2026/09/10-webmachinelearning-minutes.html , Chromium commits https://chromium.googlesource.com/chromium/src/+/0499afdbf2299ffe581a75fcb52f2da04ceba91c .
- **Fit for this net**: model must be expressed with WebNN ops (via ORT-Web WebNN EP or LiteRT.js `webnn` accelerator); attention-window ops and operator coverage not verified. With the NPU/GPU split, tensors exported to WebGPU may involve copies if device differs.

## (c) Other runtimes

- **LiteRT.js** (Google, released 2026-07-09): `.tflite` models; accelerators `wasm` (XNNPACK), `webgpu` (ML Drift), `webnn`; unsupported ops fall back to CPU (secondary source: one unsupported op may push the whole graph to CPU). PyTorch via `litert-torch` converter. TF.js interop (`runWithTfjsTensors`, needs the TF.js WebGPU backend); advice to share the GPU device with TF.js. Docs do not describe a three.js-style device share or GPU-buffer IO. https://developers.google.com/edge/litert/web/index , https://developers.googleblog.com/en/litertjs-googles-high-performance-web-ai-inference/ , comparison numbers are mixed (3.15x vs ORT WebGPU on efficientnet, 1.11x on inception_v3; browser/version undisclosed; secondary).
- **TensorFlow.js WebGPU backend**: still referenced as the interop component for LiteRT.js; no 2026 roadmap or deprecation announcement found. TF.js's backend can import a user device (`tf.setBackend('webgpu')` then device options; details unverified). Conv2D/attention ops exist; U-Net-sized models run, but not verified for this model.
- **transformers.js** (Hugging Face): wraps ORT-Web; WebGPU guide https://huggingface.co/docs/transformers.js/en/guides/webgpu . It is a model-loading convenience layer over ORT, not a separate engine; nothing specific to image-to-image CNNs.
- **ExecuTorch WebGPU backend**: experimental, "under active development"; Dawn/Tint native, Emscripten `emdawnwebgpu` for browsers; >100 ops (mostly quantized linear / LLM kernels, SDPA, rotary), shares Vulkan partitioner so unsupported ops may fail at runtime; docs do not describe device sharing. https://docs.pytorch.org/executorch/main/backends/webgpu/webgpu-overview.html
- **torch-webgpu** (arXiv 2604.02344): out-of-tree PyTorch backend + FX-to-WebGPU compiler; a research paper; installability not verified.
- **`@huggingface/kernels`**: 207 Apache-2.0 WebGPU kernels (Sep 2026), hand-optimised ops loaded from the Hub, a low-level building block rather than a graph runtime. https://huggingface.co/blog/webgpu-kernels
- **tinygrad**: found only WebGL export examples (softwiredtech EfficientNet/YOLOv8); no WebGPU browser export found in searches. **Burn (wgpu->wasm)**, **webgpu-torch**, **MLC/TVM web**: searches returned nothing usable; not assessed.

## (d) Hand-written WGSL / render-pass inference

- **Anime4K-WebGPU** (npm `anime4k-webgpu`, plus forks): small CNN/GAN upscale, restore and denoise passes as WebGPU compute shaders for video; README has no ms numbers in what I retrieved. https://cdn.jsdelivr.net/npm/anime4k-webgpu@1.0.0/README.md . Networks are tiny (a few thousand params) compared with HaloRT.
- **ORT/TF.js/WebLLM-class engines** all ultimately hand-write WGSL per op (ORT's JSEP kernels, HF kernels), so a custom path would reuse their tiling designs.
- No OIDN web port, no web DLSS/FSR-like neural upscaler, and no three.js neural denoise node found in searches (negative result, not exhaustive). Non-neural WebGPU TAA/FSR-style projects exist but are not neural.
- No published timing for a 1M-parameter U-Net or windowed-attention net hand-written in WGSL found. Visionary's MLP decoder numbers (above) are ORT, not hand-written.
- **Compute vs render passes**: compute with storage textures/buffers gives full control (shared-memory tiles, subgroups, `shader-f16`); render-pass-over-rgba16float-array tricks are limited by 8 colour attachments (and a per-sample byte budget), array layer limits, and channel packing (4 channels/texel); extension features like f16 (`shader-f16`) are broadly available in Chromium; Safari/Firefox f16 support unverified.
- **Same device as three.js**: native: a hand-written pass is just more TSL/WGSL nodes or a compute node on the renderer's device; no copy at all.
- Effort drivers: im2col-free direct conv tiling for 3x3/1x1 convs at 8-64 channels, GroupNorm reductions, windowed attention with halo, fp16 accumulators; weights as storage buffers or textures; custom export of weights from PyTorch.
