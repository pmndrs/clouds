# Tidewater cloud transport reference audit

Read-only study of `/Users/dex/Developer/tidewater`; no files copied or executed. The active implementation is `src/sky/SkyProClouds.js` by default: `App.js` selects it unless `?oldClouds` is present; `Clouds.js` is the opt-in predecessor (`App.js:117-122`). The current implementation is explicitly a sky/cloud-shell pass with a shared panorama and ground shadow interface (`SkyProClouds.js:5-17`), not a close-range voxel renderer.

## Five transferable lessons

1. **Constrain rays before marching, then use coarse-to-fine density work.** Tidewater analytically clips rays to the curved cloud shell and ground (`SkyProClouds.js:145-168`), traverses conservative weather-map bounds, steps four times coarser while empty, and backs up/refines when density appears (`220-286`). Our `realistic-shader.ts` clips to the density box but otherwise uses a fixed number of equal steps (`65-123`); `cloudscape/shaders.ts` already takes a more suitable voxel route by testing active-cell support and skipping to voxel faces (`91-100`, `247-290`). For our direction, borrow the interval/refinement principle, while retaining cloudscape's 3D occupancy traversal.

2. **Filter density by ray and pixel footprint; preserve average extinction when fine detail disappears.** Tidewater derives base/detail LOD from distance times pixel cone angle and grows the march step with distance (`SkyProClouds.js:255-261`). Cloudscape's `detailFactor` explicitly bounds phase variation over both ray-segment length and pixel footprint, fading the modulation toward its mean instead of removing density (`cloudscape/shaders.ts:212-229`). This is directly useful for voxel fly-through, where fixed-frequency detail aliases along the ray even if screen pixels are large.

3. **Spend lighting samples adaptively and amortize neighboring work.** The active shader uses a small cone-distributed set of sun taps at increasing distances, with coarser noise LODs farther away, an early optical-depth cap, and a three-order attenuation estimate (`SkyProClouds.js:191-204`, offsets at `986-996`). It reuses that optical depth across nearby view samples until position, density, or quality mode changes (`293-305`). Our realistic experiment precomputes a 3D optical-depth cache (`realistic-shader.ts:51-63`) and estimates four scattering lobes (`77-92`); this is an alternate tradeoff. Cloudscape currently computes cache optical depth by repeated fixed midpoint steps (`cloudscape/shaders.ts:102-136`). Tidewater suggests coherent, footprint-aware tap placement/reuse as a later optimization, but its preset and shell-specific phase model are not drop-in voxel transport.

4. **Temporal accumulation needs world reprojection, validation, and neighborhood clamping.** Tidewater traces one pixel in each 4×4 block of the half-resolution history each frame (about 1/64 of full-resolution pixels, before rounding) and stores color plus depth/cost metadata (`SkyProClouds.js:50-54`, `638-656`). Its resolve reprojects the prior cloud point after subtracting wind drift, rejects invalid/out-of-view history, clamps history to current neighborhood bounds, and lowers history weight as motion grows (`704-795`). Our realistic shader deliberately has only fixed per-pixel jitter and no history (`realistic-shader.ts:103-114`). Cloudscape instead provides optional motion/depth/reactive guides for a downstream temporal pass (`cloudscape/shaders.ts:323-352`); that fits its moving resident voxel cells better than directly importing a sky-history buffer.

5. **Make cloud shadows a bounded, reusable product.** Tidewater renders a camera-centered 256² transmittance map, initially full and then one quarter of rows per frame, snaps its center to a grid with four shadow-texel spacing, and bilinearly samples with a soft edge to clear outside the map (`SkyProClouds.js:814-839`, `999-1019`; `Clouds.js:531-551`). The shadow ray integrates the layer along the key-light direction and approximates transmission with two scattering terms. Our cloudscape shades ground receivers through `lightAt` and a reference/scene shadow hook (`cloudscape/shaders.ts:200-207`, `312-319`); realistic-shader samples optical depth at the ground (`realistic-shader.ts:116-121`). A bounded cache/map can reduce repeated per-pixel shadow work, but the camera-centered map is an approximation whose coverage and update cadence must match the voxel world's size and movement.

## Limits for fly-through and voxels

Tidewater's design target is a procedural, broad sky shell at roughly 4–9.2 km altitude, with horizon fade, aerial perspective and sky-LUT lighting (`SkyProClouds.js:28-53`, `318-327`). Its view shader renders cloud radiance/transmittance for the sky background; arbitrary scene geometry remains a separate scene/background composition. The shell intersection is curved-Earth aware, which is useful for long sky rays, but its 2D weather bounds, single shell density model, and camera-centered ground-shadow map do not represent resident local 3D voxel occupancy or moving cloud-volume boundaries. For fly-through, keep cloud history depth-aware and invalidate/reproject as cells stream or rebase; for voxels, do not use a sky shell's horizon fades or assume a single cloud depth per pixel. `cloudscape/shaders.ts` already supplies 3D candidate masks, local owner-stencil extinction, stationary directional-light quadrature, and a support-edge view fade designed around a resident grid (`shaders.ts:58-100`, `102-136`, `139-158`).

## Provenance / license note

Tidewater's root `LICENSE` grants MIT terms to the repository and names DRG Software Solutions LLC (`LICENSE:1-13`). `CREDITS.md` says code is MIT and specifically says the noise, lighting, and sampling scheme in `src/sky/Clouds.js` is adapted from the same owner's Sky Pro WebGPU and published under that MIT license (`CREDITS.md:91-92`). However, active `SkyProClouds.js` says it is from `../sky-pro-webgpu` and describes renamed sky-pro code (`SkyProClouds.js:5-9`), while the credit names only `Clouds.js`; the docs do not explicitly reconcile the active file's adaptation boundary. A second documentation gap: `public/clouds/LICENSING.md` says it covers third-party textures and lists only `cirrus.jpg` for clouds (`LICENSING.md:1-3,21-23`), while the active renderer also fetches `baseShape64.bin` and `blueNoise.bin` (`SkyProClouds.js:445-478`). The repository-wide MIT statement is clear, but these file/asset provenance gaps are worth resolving before treating implementation details or bundled noise as copy-ready. This audit records behavior only and does not copy source.
