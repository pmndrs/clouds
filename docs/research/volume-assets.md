# Volumetric cloud assets for WebGPU

Research checked 2026-09-15. Scope: physically informed procedural density and authored DCC/mesh-to-VDB density feeding one cloud renderer in a plain-JavaScript Three.js desktop WebGPU app, with a later React Three Fiber (R3F) v10 layer. Distant 2D clouds are considered a separate presentation technique within the application.

## Facts

### Meshes, distance fields, and cloud density

- A mesh is a boundary; a cloud renderer generally needs a scalar density field that can be sampled through the volume. Those are not interchangeable. OpenVDB's `meshToVolume`/`meshToLevelSet` routines produce signed or unsigned distance fields. Signed conversion requires a closed surface; unsigned distance does not. [OpenVDB `MeshToVolume.h`](https://www.openvdb.org/documentation/doxygen/MeshToVolume_8h_source.html)
- Blender's Mesh to Volume modifier creates a scalar grid named `density`; its interior band and voxel-size controls make it a convenient artist-facing way to turn a mesh into a filled volume. Blender Volume objects use OpenVDB files. The modifier's presence alone does not establish a one-click VDB export path: use Blender's documented volume/geometry-node bake workflow or an external converter, and verify the resulting file in the target pipeline. A density grid still needs shaping/noise if the desired result is a billowy cloud rather than a solid mesh-shaped fog volume. [Blender Mesh to Volume](https://docs.blender.org/manual/en/latest/modeling/modifiers/generate/mesh_to_volume.html), [Blender volume objects](https://docs.blender.org/manual/en/5.2/modeling/volumes/introduction.html), [Blender geometry bake and volume file format](https://docs.blender.org/manual/en/5.2/modeling/geometry_nodes/baking.html)
- OpenVDB is the mature C++ authoring and processing library; current project license is Apache-2.0. Its mesh conversion, filtering, pruning, and file I/O make it suited to an offline asset pipeline. [OpenVDB repository and license](https://github.com/AcademySoftwareFoundation/openvdb)
- NanoVDB is OpenVDB's compact, pointerless, contiguous, GPU-friendly form. Its tree topology is static after construction, although voxel values may change. The documented graphics-language backends include CUDA, OpenCL, OpenGL, DirectX 12, OptiX, HLSL, and GLSL; the FAQ still describes WebGL support as in progress and does not document WGSL/WebGPU support. NanoVDB is part of the Apache-2.0 OpenVDB project. [NanoVDB FAQ](https://github.com/AcademySoftwareFoundation/openvdb/blob/master/doc/nanovdb/FAQ.md)
- PicoVDB is an independent, Apache-2.0 project with a TypeScript loader, WGSL library, and converters from NanoVDB and STL. Its README describes a WebGPU-oriented sparse layout using 32-bit offsets and hierarchical traversal, and labels the format/API as under active development. The STL command creates a PicoVDB **level set**, not a cloud-density grid. The README claims 50%+ smaller volumes than NanoVDB for its bunny example (64 MB to 28 MB); treat this as the project's own example, not a general benchmark. [PicoVDB README and license](https://github.com/emcfarlane/picovdb)
- NanoVDB provides the `nanovdb_convert` command and a `CreateNanoGrid` C++ conversion API for OpenVDB-to-NanoVDB conversion. PicoVDB documents conversion from `.nvdb` to `.pvdb`; whether every NanoVDB scalar type/class and multi-grid density asset is handled as needed should be checked before choosing this route. [NanoVDB build and command-line tools](https://www.openvdb.org/documentation/doxygen/NanoVDB_HowToBuild.html), [NanoVDB conversion API example](https://www.openvdb.org/documentation/doxygen/NanoVDB_HelloWorld.html), [PicoVDB converter instructions](https://github.com/emcfarlane/picovdb#converting-files)

### GPU representation and memory

- WebGPU has sampled and storage 3D textures and storage buffers. The current API exposes ordinary texture allocations; sparse residency is not a standard WebGPU texture feature. Therefore a sparse volume must be represented explicitly (for example, as a tree, page table plus bricks, or sparse storage-buffer arrays). This absence is an inference from the WebGPU resource model. [WebGPU specification: textures and limits](https://www.w3.org/TR/webgpu/)
- A dense scalar texture is the simplest baseline: one `r8unorm` voxel per cell uses approximately 2, 16, 128, and 1,024 MiB at 128³, 256³, 512³, and 1024³. `r16`/half-float doubles those figures; `rgba8` quadruples them. These are payload sizes only; CPU copies, upload/staging, mip levels, and other assets add to the working set. Devices expose a 3D texture size limit, but it does not guarantee that a large allocation will fit alongside the rest of the scene. Query limits and test allocation on target devices. [WebGPU limits](https://www.w3.org/TR/webgpu/)
- Dense 3D textures make shader sampling and early WebGPU implementation straightforward. Sparse layouts avoid storing empty regions, but require custom address lookup and can add indirection, shader complexity, and packing/streaming work. A cloud with broad low-amplitude density may be much less sparse than a narrow-band SDF.
- Three.js has `Data3DTexture`, `Storage3DTexture`, `StorageBufferAttribute`, `WebGPURenderer`, and TSL. Three's WebGPU renderer does not support `ShaderMaterial`/`RawShaderMaterial` custom materials; its documented direction is node materials and TSL. Its renderer can fall back to WebGL 2, but WebGPU-only features must be capability-gated. [Three.js WebGPU renderer guide](https://threejs.org/manual/en/webgpurenderer), [Three.js `Data3DTexture`](https://threejs.org/docs/pages/Data3DTexture.html), [Three.js `Storage3DTexture`](https://threejs.org/docs/pages/Storage3DTexture.html)
- R3F v10 has an alpha release path with WebGPU and TSL support. The release notes describe v10 features as experimental and subject to change, so keep R3F as an integration layer rather than the owner of the volume data format or converter. [R3F releases](https://github.com/pmndrs/react-three-fiber/releases)
- OpenVDB and PicoVDB are Apache-2.0; Three.js and R3F are MIT. Check licenses for individual sample assets and any DCC content separately. [OpenVDB](https://github.com/AcademySoftwareFoundation/openvdb), [PicoVDB](https://github.com/emcfarlane/picovdb), [Three.js](https://github.com/mrdoob/three.js/blob/dev/LICENSE), [R3F](https://github.com/pmndrs/react-three-fiber)

## Recommendations

1. **Build one cloud renderer in plain JavaScript with Three.js `WebGPURenderer` and TSL.** The target is a desktop WebGPU app, so use Three's WebGPU path directly and add scalable quality tiers (volume resolution, ray steps, noise octaves, shadowing, and render scale). Three's WebGPU renderer does not accept the old `ShaderMaterial`/`RawShaderMaterial` route; TSL is its supported custom-shader direction. Keep a simple 2D fallback for browsers/devices that end up on its WebGL 2 backend if fallback matters.
2. **Give every density source the same field contract and renderer path.** The physically informed procedural generator and imported Houdini/Blender/Maya or mesh-to-VDB assets should both resolve to a scalar density field with known bounds, transform, voxel size, and value range. Keep generation/import separate from sampling and compositing so the renderer can use the same raymarching, lighting, and quality controls for either source. Allow procedural generation to produce the grid directly; a mesh SDF is an optional shape/mask input, not a density field by itself.
3. **Evaluate 2D distant clouds as a separate presentation technique.** Nearby clouds need depth/parallax and use the full density raymarcher. A 2D projection/map or layered sky-shell impostor may work better for distant clouds, but do not assume it will match the volumetric look or transition seamlessly. Share parameters and art direction where useful, then validate the 2D treatment on its own.
4. **Use dense 3D textures as the first GPU representation for baked density.** Try 128³/256³ single-channel data first and profile 512³ on target desktop GPUs. Dense sampling is straightforward through Three.js `Data3DTexture`; use PicoVDB/NanoVDB only after a real field demonstrates that empty-space storage or larger spatial extent justifies sparse traversal. Sparse bricks plus a page table are a simpler next comparison than adopting a full tree immediately.
5. **Treat PicoVDB as a sparse-path experiment, not an assumed final dependency.** Its TypeScript/WGSL work is close to the WebGPU target and may help for SDF masks, CSG-shaped assets, or highly sparse volumes. First confirm that the desired scalar density grids convert and sample correctly, then compare visual quality, GPU time, upload size, and memory against dense textures. Its unstable format/API and documented level-set STL workflow make an adapter/prototype safer than coupling renderer code to Pico structures.
6. **Keep one renderer-independent asset contract across the monorepo.** Preserve dimensions, voxel size, world/index transform, bounds, semantic (`density` vs `SDF`), value range, background value, and channel type in metadata. Put file parsing and coordinate/value semantics in a shared package; keep the Three.js upload and sampling adapter separate; then let R3F v10 own scene composition and lifecycle. TSL can target WGSL or GLSL, but a raw PicoVDB WGSL library is not automatically a drop-in Three node, so plan a shader-language adapter or a deliberately separate custom pass.

## Unknowns to resolve with a prototype

- Does the current PicoVDB converter preserve a Blender/OpenVDB `density` grid with the required scalar type, grid class, transform, background, and multi-grid metadata? The README establishes NanoVDB conversion, while a January 2026 open issue asks about RGBA fog data and has no response; neither proves support or non-support for scalar density. [PicoVDB converter](https://github.com/emcfarlane/picovdb#converting-files), [open fog-data question](https://github.com/emcfarlane/picovdb/issues/1)
- How much of the desired cloud survives quantization to 8-bit? Compare banding and extinction response against half-float or float at target output. A gradient/noise cloud may need more than 8 bits even when shape masks do not.
- What is the actual sparse break-even point? Measure density occupancy at several thresholds and compare memory plus shader traversal cost. Narrow-band distance fields are naturally sparse; fluffy clouds with wispy density tails may not be.
- What visual and performance tradeoff does a distant 2D cloud treatment offer against full 3D raymarching at the app's actual camera speeds, cloud altitude, and lighting model? Test the 2D presentation on its own rather than assuming a seamless transition.
- Does the physically informed procedural generator produce a density grid on CPU, GPU, or both, and which resolution/precision tiers meet its visual and frame-time target?
- Can a PicoVDB WGSL shader library be integrated cleanly with the intended Three.js WebGPU/TSL material path, or should it remain a separate raw-WebGPU pass? Three documents TSL as its WebGPU shader path, but PicoVDB demonstrates raw WGSL for direct WebGPU.
- What are the target browser/device limits and bandwidth? The WebGPU spec defines per-device limits, not a portable budget for simultaneous volume assets or their upload cost. Query actual device limits and profile on representative integrated and discrete GPUs.
