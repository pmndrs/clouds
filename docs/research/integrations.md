# Three.js integration research

**Checked:** 2026-09-15. “Vanilla” here means framework-free JavaScript using Three.js. The product target is desktop WebGPU, with one Three.js TSL implementation and a later React Three Fiber (R3F) adapter. The primary experiences are volumetric clouds and distant clouds. Distant clouds may use the same full volumetric renderer or a cheaper 2D layer. Procedural and imported VDB data are density sources for the volumetric renderer; the 2D layer can share weather/lighting controls without sharing a 3D sampling contract.

## Architecture update — 2026-09-16

The original TSL-only recommendation below is superseded: TSL, embedded WGSL and direct compute/render passes on Three’s device can coexist. The author’s [upscaler code](upscaler-integration.md) demonstrates raw compute and Three-owned texture sharing inside node scheduling. Required features should not be deferred due to TSL limitations. R3F v10 is mandatory; current tested revisions will be pinned during implementation. Sky integration can evolve with the author’s packages.

## Original research recommendation

Build the rendering API as a normal Three.js package exposing scene content and/or TSL composition passes, with explicit update and disposal hooks. A depth-aware volumetric pass may need integration beyond an Object3D mount. Use `WebGPURenderer` with TSL plus embedded/direct WGSL as appropriate (updated after upscaler inspection). This keeps the browser-facing API usable from plain JavaScript first, while an R3F package can mount the same objects and call the same update hooks later. Three’s WebGPU renderer supports a WebGL 2 fallback, and TSL is designed to compile to WGSL or GLSL for the selected renderer backend. That fallback does not make arbitrary GLSL materials portable: custom `ShaderMaterial` code and `onBeforeCompile()` patches are explicitly unsupported by `WebGPURenderer`. [WebGPURenderer docs](https://threejs.org/docs/pages/WebGPURenderer.html), [WebGPU renderer manual](https://threejs.org/manual/en/webgpurenderer.html)

For a ready atmospheric backdrop, Three’s `SkyMesh` is the closest built-in WebGPU starting point. For a more physically based atmosphere, solar-position controls, and aerial-perspective haze, `@pmndrs/sky` is a useful optional integration. Neither replaces a volumetric cloud renderer: `@pmndrs/sky` explicitly lists volumetric clouds as out of scope, while Three’s volume-cloud example is a small TSL raymarching demonstration rather than a maintained cloud package. [SkyMesh docs](https://threejs.org/docs/pages/SkyMesh.html), [pmndrs/sky README](https://github.com/pmndrs/sky), [Three.js WebGPU volume cloud example](https://threejs.org/examples/webgpu_volume_cloud.html)

## Current Three.js sky and cloud APIs

| Option | What it provides | Backend and integration notes |
| --- | --- | --- |
| [`SkyMesh`](https://threejs.org/docs/pages/SkyMesh.html) | An analytical Preetham sky dome with sun position and atmospheric scattering controls. Current properties include `cloudCoverage`, `cloudDensity`, `cloudElevation`, `cloudScale`, and `cloudSpeed`. The official example constructs `new SkyMesh()`, scales it, adds it to the scene, and tunes its `UniformNode` properties. | An addon in `three/addons/objects/SkyMesh.js`; **WebGPURenderer only**, implemented with `NodeMaterial` and TSL. It includes a procedural, screen/dome-projected 2D cloud mask, not full volumetric clouds. Good as a distant/cheap sky layer or a reference for controls and presets. [Source](https://github.com/mrdoob/three.js/blob/dev/examples/jsm/objects/SkyMesh.js), [official example](https://github.com/mrdoob/three.js/blob/dev/examples/webgpu_sky.html). |

This is a clear reference for the volumetric path, but it is an example with a generated 128³ test volume, not a reusable library or a complete weather-cloud system. [Source](https://github.com/mrdoob/three.js/blob/dev/examples/webgpu_volume_cloud.html). |
| [`Sky`](https://threejs.org/docs/pages/Sky.html) | The older analytic skydome with tunable scattering uniforms. | WebGLRenderer only. The docs direct WebGPU users to `SkyMesh`; Drei’s `<Sky>` wraps the older Three sky API, so it is not the target for a TSL/WebGPU core. [Three Sky docs](https://threejs.org/docs/pages/Sky.html), [Drei Sky source](https://github.com/pmndrs/drei/blob/master/src/core/Sky.tsx). |
| [`@pmndrs/vanilla` Cloud/Clouds](https://github.com/pmndrs/drei-vanilla) | A framework-free port of Drei helpers. Its `Cloud` groups many instanced textured plane segments into stylized billowy shapes; `Clouds.update(camera, time, delta)` updates the group. | Published as `@pmndrs/vanilla`, MIT licensed, and useful as a vanilla→R3F precedent. Its cloud material patches Three shader chunks through `onBeforeCompile()`, so it is a **WebGL-style path** and is incompatible with `WebGPURenderer` per Three’s renderer guide. It is not a volumetric cloud system. [Cloud API/source](https://github.com/pmndrs/drei-vanilla/blob/main/src/core/Cloud.ts), [package README](https://github.com/pmndrs/drei-vanilla). |

The current WebGPU sky object is a real scene `Mesh`, which makes it straightforward to add to a vanilla scene or mount as an R3F primitive. In contrast, `Scene.background` accepts a color or texture (including cube/equirectangular skyboxes), and `Scene.environment` supplies an environment map to physical materials. A mesh cannot be assigned to either property. Put near-camera clouds and the procedural dome in the scene graph. If clouds should contribute to reflections/IBL, generate or provide a separate environment texture; do not assume visible `scene.background` also lights the scene. [Scene docs](https://threejs.org/docs/pages/Scene.html), [Three backgrounds and skyboxes manual](https://threejs.org/manual/en/backgrounds.html)

This distinction also matters for compositing. Three’s manual notes that a scene background texture can be processed by post effects when rendered through Three, while an object mesh gives the cloud layer normal scene depth and render ordering. A library should expose cloud `Object3D` content separately from optional background/environment assignment; avoid silently replacing a host application's `scene.background` or `scene.environment`.

## pmndrs atmosphere option

[`@pmndrs/sky`](https://github.com/pmndrs/sky) is a real, currently published pmndrs package, not a hypothetical “sky plugin.” It is a Three.js/TSL WebGPU atmospheric system based on Sébastien Hillaire’s 2020 technique. The vanilla API is `new Sky(renderer, options)`, `sky.attach(scene)`, per-frame `sky.update(camera)`, and `sky.dispose()`. `attach(scene)` sets both `scene.environment` and `scene.background`; its optional `applyHaze()` adds an aerial-perspective post-process. It has earth, mars, and titan atmosphere presets plus sun/time controls. The project README marks its code MIT licensed. [README and API overview](https://github.com/pmndrs/sky), [MIT license](https://github.com/pmndrs/sky/blob/main/LICENSE)

Treat it as an optional atmosphere/IBL provider alongside the cloud renderer. It currently says volumetric clouds and god-rays are out of scope, and its `attach()` owns both scene slots, so a host app needs an explicit choice about which system controls background/environment. `SkyMesh` already offers a lightweight 2D procedural cloud field; a volume renderer remains a separate layer. The two can therefore cover the requested distant and near-field experiences without treating the cheap sky mask as volumetric density.

## R3F v10 status and migration shape

R3F v10 **has not shipped as a stable release** in the registry snapshot checked on 2026-09-15. npm reports stable `@react-three/fiber` 9.7.0 as `latest`, while `10.0.0-alpha.5` is tagged `alpha` and was published five days before this check. The official alpha 4 release was dated 2026-08-28 and describes WebGPU/TSL hooks including `useUniforms`, `useNodes`, `useLocalNodes`, and `useRenderPipeline`; the release explicitly calls the alpha features experimental. [npm versions/tags](https://www.npmjs.com/package/%40react-three/fiber?activeTab=versions), [R3F alpha 4 release](https://github.com/pmndrs/react-three-fiber/releases/tag/v10.0.0-alpha.4)

`@pmndrs/sky` publishes React bindings and states that they need `@react-three/fiber >=10.0.0-alpha.4`; its README warns that earlier 10.x canaries can fail at module load. This confirms an active integration target, while also reinforcing that v10 is still moving. For a later adapter, keep React out of the core package: mount the core object under the R3F scene and drive its update method from the frame loop. If exposing a declarative sky wrapper, put it in a separate React entry point. Do not infer that the stable R3F line is WebGL-only; the v10-specific hooks and sky binding requirements are the relevant constraints for this proposed adapter.

## Suggested compatibility contract

1. The vanilla package owns Three objects and TSL nodes only. Its public entry point should not require React; its implementation may use raw WebGPU through the renderer device bridge.
2. Model close volumetric clouds and the far sky/distant cloud layer as separate scene/compositing layers sharing compatible public weather and lighting controls. Use a `SkyMesh`-style projected layer only as a deliberate low-cost distant representation.
3. Let applications decide whether to use built-in `SkyMesh`, `@pmndrs/sky`, or their own background. Keep scene-background and environment-map assignment opt-in because these are host-wide scene settings.
4. Add the R3F wrapper after the vanilla object lifecycle is stable. As of this research date, test it against a pinned v10 alpha (at least alpha.4 for `@pmndrs/sky`'s React bindings) and expect API movement until v10 reaches stable.
5. Do not base the WebGPU target on Drei `Cloud` or `@pmndrs/vanilla` `Clouds`; their instanced sprite aesthetic and GLSL shader-chunk edits solve a different WebGL problem.
