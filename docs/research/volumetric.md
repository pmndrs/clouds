# Volumetric cloud rendering research

**Research snapshot:** 2026-09-15  
**Scope:** volumetric rendering paths and reusable precedents for a framework-free Three.js library using `WebGPURenderer`/TSL first, with a later R3F v10 adapter. Desktop WebGPU is the initial quality target; browser/mobile portability still needs a separate quality profile.

## Focused follow-up

The R2 coverage review prompted direct reading of the 2022/2023 slide PDFs: [distance rendering, LOD distinctions and P2 revision](nubis-lod.md). This adds page-specific evidence beyond the original survey. Performance techniques and impostor ideas for the later perf pass are collected in [cloud-perf-tricks.md](cloud-perf-tricks.md).

## Findings at a glance

- **Decima/Nubis is a family of systems, not one renderer.** The 2015/2017 lineage describes a procedural, mostly 2.5D sky system built from weather/type maps, profile functions, tiled 3D shape/detail noise, ray marching and lighting approximations. The later Nubis³ work (SIGGRAPH 2023) explicitly moves to authored voxel clouds for close-up flight-through scenes. It adds SDF-guided ray-march skipping, an up-res strategy for dense voxels, lighting acceleration, and cloud-specific lighting approximations. These are different density and authoring regimes that can still feed one renderer through a shared density-sampling contract.
- **No public Decima renderer implementation was found in the reviewed sources.** The public source material is talks/slides plus a cloud-data pack. Guerrilla's 2023 abstract says the pack is provided so developers can try building a similar renderer, but its assets are not a source-code license. A Guerrilla artist's account describes the Burning Shores storm workflow: Houdini with in-house Atlas tools, simulated pieces from an in-house Aero fluid solver, voxel edits for the cave, then rendering/lighting effects in Nubis. The in-house tools and runtime remain unavailable.
- **Unreal provides a current production reference, not portable code.** UE 5.8's official documentation describes ray-marched 3D volume textures, approximate multiple scattering, Beer shadow maps versus secondary shadow marching, reduced-resolution reconstruction modes, and conservative-density early-outs. Its engine source is available to licensees under Epic's EULA; it is not permissively licensed source for an independent npm package.
- **Takram is the closest Three.js library precedent, but its shipped clouds are presently GLSL/WebGL.** The cloud package is MIT, is already usable from vanilla Three.js or R3F, and has real layers, BSM shadows, cloud resolve/temporal upscaling and aerial-perspective integration. The repository's separate TSL/WebGPU rewrite marks clouds as work in progress; the package README still says its cloud shaders do not support WebGPU. Treat those as distinct states.
- **Recommended direction:** build the first volumetric prototype as a Three.js `WebGPURenderer` + TSL renderer over a regular 3D density texture and bounding volume, then add sparse authored volumes behind a data-source interface. Do not make a new VDB runtime format the first milestone. Reuse the Nubis papers for algorithms, the official Three.js volume-cloud example as the minimal TSL/3D-texture proof, and Takram's cloud package for the mature atmosphere/temporal/shadow integration reference.

## Decima / Guerrilla Nubis: what is documented

| Public milestone | Documented system | Implication for this library |
| --- | --- | --- |
| 2015, *The Real-Time Volumetric Cloudscapes of Horizon: Zero Dawn* | Procedural cloudscapes for broad sky coverage and multiple cloud types; the prototype target was under 2 ms on PS4. The public paper/course material is about the early cloudscape approach. | Strong basis for an efficient far-field sky layer, but not a complete close-up voxel asset renderer. |
| 2017, *Nubis: Authoring Real-Time Volumetric Cloudscapes with the Decima Engine* | Production concerns include regional authoring, animation/transitions, atmosphere integration and further optimization. It discusses procedural weather, Perlin-Worley noise and the lighting model. | Treat authoring, time/weather control and compositing as core parts of cloud rendering, not only a density shader. |
| 2022, *Nubis, Evolved* and GDC superstorms | The sky system is extended to fly-through environments and superstorm VFX with rapid motion/internal lightning. The talk describes fast cloud results at 1080p without temporal upscaling for close environments, and a different temporally-upscaled path for rapidly moving clouds. | One renderer must not assume a stationary sky camera or one fixed resolution/reconstruction strategy. |
| 2023, *Nubis³* | Voxel clouds act as skyboxes and explorable environments. Published techniques include compressed signed-distance-field ray-march acceleration, fluid-simulation-based modeling, up-resolving dense voxel data without memory-access bottlenecks, light-sampling acceleration, dark-edge and inner-glow approximations. The course page says the authors were leaving behind their established 2.5D methods in favor of voxel clouds for these use cases. | Voxel clouds are the latest publicly detailed Decima path found in this research for immersion, but the talk describes significant data-authoring and memory/lighting engineering beyond ordinary ray marching. |

The voxel term needs care: this does **not** mean Nubis³ is just a mesh voxelizer or an off-the-shelf VDB viewer. The SIGGRAPH 2023 material describes a bespoke authoring/rendering pipeline. A Guerrilla artist says the Burning Shores storm volume was modeled with Houdini and internal Atlas tools, with component cloud pieces generated by an internal Aero solver and edited with internal voxel tools. That suggests the relevant portable concept is a structured volume asset plus cloud-specific authoring, not simply “turn any mesh into VDB.”

The Nubis voxel-cloud pack is linked from Andrew Schneider's publication page and is described as containing two cloud NVDFs, a noise generator and voxel/noise data in TGA slices and VDB archives. Schneider clarified publicly that the examples are lower resolution and intended as source data for people to build a similar renderer; they are not a ready-to-use high-resolution production cloud set. No clear license for redistributing the pack was found in the public landing material. Keep it out of the library/package until its individual asset terms are reviewed.

## Unreal Engine production reference

Epic's current UE 5.8 documentation says the built-in Volumetric Cloud component ray marches 3D volume textures and approximates complex participating-media lighting for real-time use. It exposes several useful design lessons:

- Use artist-defined volume materials and cloud textures, with time-of-day coupling to Sky Atmosphere and Sky Light.
- Approximate multiple scattering with a small number of extra transmittance octaves; Epic recommends a low setting for game budgets.
- Choose between secondary ray marching for sharper/colored near shadows and Beer Shadow Maps for faster, longer-distance cloud shadows.
- Offer reactive quality modes that trace at quarter or half resolution and reconstruct/upsample, because fly-through and ground-to-space transitions benefit from responsiveness.
- Let artists supply conservative density/coverage data so the renderer can reject empty cloud samples before evaluating expensive density, albedo and extinction.
- Do not assume every cloud contributes to full ray-traced reflections; Epic notes the cost is significant and handles cloud contributions through sky-light capture.

Epic makes Unreal Engine source available to linked GitHub accounts/licensees under its EULA. The EULA constrains how Engine Code can be distributed and permits public discussion snippets within a stated line limit. For this project, use the official docs and public algorithm papers as technical references; do not copy Unreal engine implementation code into a standalone MIT/BSD package. This is a conservative project boundary, not legal advice.

## Proposed staged Three.js/WebGPU path

1. **Make a TSL ray-march prototype over a regular `Data3DTexture`.** Start with a box/shell intersection, one scalar density field, Beer-Lambert transmittance, Henyey-Greenstein phase lighting, early opacity termination, and one directional light. Keep it framework-free and consume a Three.js scene/camera. The official Three.js example verifies the basic texture/raymarch/TSL route; the first acceptance scene should test opaque geometry depth integration, not only an isolated cube.
2. **Use one renderer with interchangeable density sources.** Define a common density/attribute sampling contract that the same ray marcher can query from procedural functions, imported VDB data baked to dense 3D textures, or hybrids such as a voxel profile eroded by procedural detail noise. Each source may provide optional bounds, coarse occupancy or SDF data to accelerate traversal. Output color/transmittance and compositing metadata from the renderer; keep TSL pass/resource lifecycle hooks explicit so the later R3F package can remain a thin adapter.
3. **Add an authored close-up cloud profile as another source for the same renderer.** Use prepared volume profile channels plus tileable 3D detail noise; add adaptive step size and an optional occupancy/SDF lower-detail field for empty-space skipping. Do not couple this asset format to PicoVDB until it supports needed density/attribute grids and has stabilized.
4. **Add lighting and scene integration in measured steps.** First directional-light self-shadowing via short secondary marches; next a lower-resolution light-density/Beer map for long-distance shadow and reduced-cost ground shadow; then ambient multiple scattering, ground bounce and atmospheric depth composition. Allow each expensive feature to be disabled independently.
5. **Add temporal reconstruction only with a clear reprojection contract.** Store prior cloud color/transmittance and motion/reprojection data. Test camera cuts, fast camera movement, thin clouds, disocclusion against scene geometry and moving volumes. Takram and Unreal both show reconstruction/scalable resolution are fundamental costs, but Takram's own documented ghosting is a warning to keep the baseline renderer valid without temporal history.
6. **Prototype the sparse asset track separately.** Convert Houdini/OpenVDB volumes offline. Compare (a) dense 3D texture bake, (b) brick/atlas with a coarse occupancy hierarchy, and (c) PicoVDB/NanoVDB-style sparse buffers. Measure download bytes, GPU memory, samples/frame and camera-through-volume frame time on representative desktop GPUs. Pick an interchange/runtime format only after measuring actual authored cloud assets.
7. **Then expose R3F v10.** Keep React-specific lifecycle/material updates separate from the vanilla renderer core. R3F should own attaching/updating the renderer object; Three.js renderer state and GPU resource disposal remain explicit.

### Risks and open technical questions

- The current Three.js example proves 3D texture ray marching, not fast volumetric cloud shading. It can validate TSL integration but should not set quality expectations.
- A cloud-shaped signed-distance field is useful for traversing empty space, but it is not the cloud's extinction/density. The authored format may need several fields (coarse profile/coverage, shape type, density scale, fine noise, optional temperature/emission) plus physical scale and transforms.
- A 3D texture route is simple and appropriate for bounded authored clouds, but large sparse global clouds stress texture memory and loading. A true sparse route adds data-format stability, WGSL layout, filtering, LOD and streaming complexity.
- TSL/WebGPURenderer/Three.js APIs evolve. The Takram WebGPU rewrite being in progress is evidence to pin supported Three.js revisions and keep our core's GPU-facing layer small.
- Browser WebGPU capabilities, 3D texture dimensions, filterable formats and compressed 3D texture support vary. Probe adapter/device features and provide quality fallbacks instead of assuming optional compression.
- Full cloud-shadow integration into arbitrary Three.js scenes is a larger integration problem than rendering a transparent fullscreen cloud image: scene-depth handling, color space, HDR, tone mapping, aerial perspective, transparency and per-material shadowing need explicit contracts.

## Questions to settle in the main spec

1. Which views must the shared renderer support at launch: bounded fly-through cloud volumes, a planet-scale cloud shell, or both? One density API can support both, but bounds, camera ranges and acceleration data differ.
2. Should the initial data path bake authored OpenVDB/mesh assets into dense 3D textures, with sparse OpenVDB/NanoVDB import added later, or is sparse import a launch requirement?
3. What is the first desktop baseline (GPU tier, resolution, FPS and target maximum memory)? Voxel rendering and multi-pass reconstruction budgets cannot be meaningfully specified without this.
4. Does v1 need cloud shadows on scene geometry and reflections, or is correct cloud color/transparency compositing the first deliverable?
5. Should the existing MIT-licensed Takram package be a candidate dependency/upstream collaboration for layered clouds, or should the library build an independent renderer/API from the start?
