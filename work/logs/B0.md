# B0: budget (network inference vs our raymarch)

Date 2026-11-25. Agent: Sonnet. Measurement only; no rendering code changed. M5 Pro, headless Chrome 158 (Metal), load 3-5 (other apps open: best effort, not a quiet pass).

## Table (ms)

| pixels (queries) | network default 64->5x64->3, f16 | same, f32 | network compact 64->3x32->3, f16 (ESTIMATE) | our raymarch, Disney cloud |
|---|---|---|---|---|
| 128^2 (16,384) | 1.69 | 1.50 | ~0.35 | not measured (page never became ready at 128x128); 192x192 gives 1.1 |
| 256^2 (65,536) | 6.33 | 9.04 | ~1.3 | 1.1 to 1.3 |
| 512^2 (262,144) | 24.58 | 39.19 | ~5.0 | 1.0 to 1.1 |

Compact is NOT measured: `mlp-timing` hard-codes `DEFAULT_SHAPE` and has no `network=` argument (only mlp-check / nrc pages do). The estimate scales the default by multiply-adds per query: default 5 layers of 64x64 plus 64x3 = 20,672; compact 64x32 + 2x32x32 + 32x3 = 4,192; ratio 4.9. Real kernels do not scale exactly with MACs.

Context: the 512^2 f16 default figure (about 94 ms per million queries) matches the earlier N2 figure.

## How each was timed

- Network: `mlp-timing` page, per-pass GPU timestamps (timestamp-query) of `encodeInfer`, 30 repeats after 3 warm-up passes, median; portable kernel (`infer=portable`, the default), image-task encoding computed in-kernel (no input/feature reads, no readback inside the timing). Output is 3 floats per query.
- Raymarch: `window.__clouds.runtimeTiming(30)` from `/reference-pt/`, quality high, nubis lighting, view nubis-noon, 90 settle frames. WALL time `runtime.encode` to `onSubmittedWorkDone`, median of 30, with 0.1 ms resolution (the browser timer is coarsened). It excludes the three.js sky draw. Same cloud framing code at each size (camera ring and fov fixed), so the cloud covers about the same fraction of the frame.

Not comparable: network = GPU timestamps of one pass; raymarch = wall time (includes submit and queue latency, floor about 1 ms) and the whole runtime frame (light update, march, temporal). The raymarch number is flat across sizes (1.0 to 1.3 ms from 192 to 512), so it is dominated by a fixed cost or the timer floor; its per-pixel cost at these sizes cannot be read from it.

## Full-sky frame (c)

A ready bench exists: `/hzd/` run through `scripts/gpu/bench-sweep.mjs` (rAF frame time plus per-pass GPU timers, `gpuLast`). Two tries did not give a cloud-bearing number: the first timed out at "ready" (vite dependency re-optimisation on first load of the page), the second ran but the sky-layer trace pipeline never appeared in the GPU timer and the capture shows clear sky, so its 0.2 ms frame is not a cloud frame. Needs a longer pipeline-compile wait ("minutes under load" per the script header). No number recorded.

## B0c: full-sky frame cost, got it

The earlier failure was not a compile wait. Passing `--base '{"c.animSpeed":0}'` (which calls `__tune.apply`) left the sky layer out of the GPU timers and gave 0.2 ms rAF frames; with `--base '{}'` the same script works. `capture.mjs` (no apply) also showed the sky pass. No script change.

Machine: M5 Pro (apple metal-3), headless Chrome, load average 5-8 from other sessions (some noise). 1280x720, `/hzd/` page, procedural cloudscape through packages/runtime, sun/camera at the bench bookmarks.

    CLOUDS_NO_WATCH=1 npx vite --port 5332 --strictPort
    echo '[{"name":"base","set":{}}]' > cfg.json
    node scripts/gpu/bench-sweep.mjs --url "http://localhost:5332/hzd/?quality=ultra&clean=1" --base '{}' --views gp7,horizon --reps 2 \
      --configs cfg.json --out work/captures/B0/fullsky-ultra.json --size 1280x720 --frames 100 --settle 200     # same with quality=high, reps 1
    node scripts/gpu/capture.mjs --url "http://localhost:5332/hzd/?quality=ultra&clean=1" --size 1280x720 --settle 200 --shots gp7 --out <dir>

Timing: frame ms = rAF interval over 100 frames (3 windows, median), vsync and frame limit off so it is GPU-bound; cloud pass = median of the per-pass GPU timestamp for `skyLayer` (the procedural trace; 4-5 samples per run). Other passes (dome, shadowMap, marchNear/Far, composite, skyResolve) are each under about 1.3 ms, together about 1-2 ms.

| quality | view | frame ms (rAF) | skyLayer ms (GPU) |
|---|---|---|---|
| ultra | gp7 | 15.3, 15.7 | 14.6, 14.9 (min 14.4) |
| ultra | horizon | 11.5, 11.4 | 10.6, 10.6 |
| high | gp7 | 8.3 | 7.8 |
| high | horizon | 7.3 | 6.4 |

Ultra is the page default. skyLayer is about 93-95 % of the frame. The capture.mjs runs gave skyLayer 17.5 ms (gp7, ultra, total 20.6) and 10.5 ms (horizon), i.e. a few ms noisier because that script does not turn vsync off.

Screenshot work/captures/B0/fullsky.jpg (gp7, ultra, 1280x720): clouds on screen, roughly half the frame is cloud (large cumulus mass top left and centre, a bank of smaller cumulus across the lower half, blue sky top right). It is a cloudscape, not a 100 % overcast fill. The horizon view (ground plane in the lower half) has clouds over the upper ~45 % of the frame.

Caveats: ultra renders the sky layer at skyScale 0.75 (960x540 here), high at 0.5, so the ultra number is for an upscaled-from-lower-res trace, not full 1280x720 marching; cloud pass cost scales with cloud coverage and the view (gp7 is 4 ms above horizon); scene is static (no wind advance), temporal reprojection is warm; GPU shared with other sessions' load.
