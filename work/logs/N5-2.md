# N5.2: pt_to_tza.py converter

`scripts/neural/pt_to_tza.py`, Python standard library only (no torch, no numpy).

## Usage

```
python3 -I scripts/neural/pt_to_tza.py [--fp16] [--verify] [--list] [--out DIR] halo_dir.pt halo_env.pt
```

Default output dir `/Users/dex/Developer/WebGPUClouds/artifacts/research/neural/weights/`
(local only, not committed): `halo_dir.tza`, `halo_env.tza` (`--fp16` writes `*.fp16.tza`).

Source `.pt` files: HaloRT (MIT) `halort/pretrained/`. The `.pt` is read with a
restricted `pickle.Unpickler`: only `collections.OrderedDict`,
`torch._utils._rebuild_tensor_v2`, `_rebuild_parameter` and `torch.*Storage` (stub
objects) are allowed; any other global raises. Storages are read from `<name>/data/<n>`.

Format written (matches Denoiser `tza.ts` `parseTZA`): 12-byte header (magic 0x41d7,
major 2, minor 0, u64 table offset), padded to 64; tensor data 64-byte aligned; table at
the end (u32 count; per tensor u16 name_len, name, u8 ndims, u32 dims, one layout char per
dim (`oihw`, `oi`, `x`), dtype `f`/`h`, u64 data offset). Keys unchanged (`_orig_mod.`
stripped if present; none were present). Shapes native (OIHW).

## Result

```
halo_dir.pt -> halo_dir.tza : 273 tensors, 1151649 parameters, 4619287 bytes
halo_env.pt -> halo_env.tza : 273 tensors, 1151649 parameters, 4619287 bytes
```

Matches ENGINE.md (273 tensors, 1,151,649 parameters). Both files have identical key
sets and shapes. fp16 output is 2,318,487 bytes.

Checks passed:
- `--verify` (own stdlib reader, element-wise independent gather from the .pt storages):
  `init_conv.weight [16,8,3,3]`, `downs.3.2.mem_kv [2,4,8,4]`, `final_conv.bias [1]`
  bit-identical, for fp32 and fp16 (fp16 compared against struct 'e' rounding).
- Denoiser `parseTZA` (run with `node --experimental-strip-types`, from the Denoiser
  worktree, nothing modified): reads `halo_dir.tza`, 273 tensors, 1,151,649 elements,
  `final_conv.bias` = [-0.1008...].

## Odd: weights are stored channels-last (strided views)

Every conv weight and every `mem_kv` in the state dict is a non-contiguous view. For
example `downs.0.0.block1.proj.weight` has shape `[16,16,3,3]` but strides
`(144,1,48,16)`, i.e. memory order O,H,W,I (NHWC-style, the model was run
`channels_last`). `mem_kv [2,4,8,4]` has strides `(128,1,16,4)`. Reading the raw storage
as if contiguous would silently scramble the weights. The converter gathers by stride
into logical row-major order, so the `.tza` holds the logical OIHW tensors that
`parseTZA` and ENGINE.md §6 assume. Anyone reading the `.pt` storages directly (for a
parity script, say) must apply the strides.

Other: `norm.g` is shape `[C]` (not `[1,C,1,1]`); `final_conv` is a 1x1 `[1,16,1,1]`;
all tensors are float32; no `_orig_mod.` prefixes, no buffers, no `num_batches_tracked`.
