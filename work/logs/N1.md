## Repeat

```

python3 -I -m http.server 8765 --bind 127.0.0.1 --directory artifacts/research/neural/rdv_on_the_web &
node scripts/neural/time-demo.mjs --pad --base http://127.0.0.1:8765 --out work/captures/N1 ; kill %1
```

Chrome flags: `--enable-unsafe-webgpu --enable-webgpu-developer-features --disable-dawn-features=disallow_unsafe_apis`. The demo loads onnxruntime-web 1.30 from jsdelivr (network needed).

## Caveats (read before trusting the split)

- Without `--pad` every timestamp reads 0 on Metal: the demo's `mark()` writes timestamps in EMPTY compute passes and Metal drops them. `--pad` injects (via CDP, demo files untouched) one trivial dispatch into each timestamp pass; then values are nonzero.
- The split looks unreliable. "features" of 0.05-0.1 ms is implausible for a ray-marched 17-channel feature kernel, and GPU per frame is only 23-45 % of the frame interval (page itself says "GPU busy 23%" at 512 fp32). Likely causes: the features kernel is not between marks 0 and 1 on the GPU timeline (wait:false, separate submits), and/or Metal reordering or idling between submits. Treat "network" as a floor and "features" as unmeasured.
- Interval = wall time between frames finishing, 3 frames in flight, replay cache of 1395 kernels in one submit.

## What dominates

- The network is the only stage the timestamps can see, and it scales about 3.6x for 4x pixels (10.7 to 38.8 ms): it is GPU-bound and roughly linear in pixel count.
- Frame interval is 4 to 4.3x the measured GPU time at both resolutions: most of each frame is outside the timestamped span (features kernel, submit gaps, or inter-frame idle). Resolving that needs a per-dispatch timer around the features evaluate or a `queue.onSubmittedWorkDone` wall time per stage.
- fp16 helps the 6-pass network by 6 to 16 % (512: 38.8 to 32.7 ms) but not 256, and is slower on sun-only (13.6 to 17.6 ms, noisy).
- Sun-only (1 pass) at 512 runs at 27-30 ms per frame (about 35 fps) versus 140-168 ms for the 6-pass page: about 5x cheaper, i.e. the sky passes are most of the cost.

## N1b: where the frame goes (512², forced serial, M5 Pro)

Script `scripts/neural/time-overhead.mjs` (injected JS only; wraps `GPUQueue.submit`, `GPUComputePassEncoder` calls and `beginComputePass`; serial mode delays the page's `nextTask()` until `queue.onSubmittedWorkDone()` so one frame is on the GPU at a time). Median of last 20 frames. Stage wall = from the stage's mark submit to `onSubmittedWorkDone` after it. Raw: `work/captures/N1b/overhead.json` (if present) or rerun the script.

| config | features wall ms | network wall ms | frame wall ms | interval ms | network encode CPU ms | passes | dispatches | setBindGroup | setPipeline |
|---|---|---|---|---|---|---|---|---|---|
| fp16, replay on, pipelined (page default) | n/a | n/a | n/a | 143.9 | 0.5 | 276 | 1825 | 1825 | 1825 |
| fp16, replay on, serial | 6.5 | 135.3 | 141.8 | 142.3 | 0.5 | 276 | 1825 | 1825 | 1825 |
| fp32, replay on, serial | 6.7 | 162.1 | 168.9 | 169.5 | 0.4 | 225 | 1395 | 1395 | 1395 |
| fp16, replay OFF (plain ORT), serial | 11.7 | 130.5 | 142.1 | 142.6 | 43.1 | 276 | 1825 | 1825 | 1825 |

Accumulate is under the timer resolution (queued behind the network). Page's GPU timestamps for the same fp16/fp32 runs: network 32.7 / 38.8 ms.

- The frame is the network stage: 135 ms of 142 ms wall (fp16), features about 6.5 ms. Pipelining 3 frames in flight does not hide it (interval equals serial wall time), so the GPU queue is the bottleneck, not the CPU.
- The page's timestamps see only 33 ms of those 135 ms. About 100 ms (76 percent) of the network stage is outside the timestamped span, which is consistent with the hypothesis that it scales with dispatch count: 1825 dispatches, one pipeline and one bind group set each, in 276 passes, is about 55 us of unaccounted time per dispatch (fp32: 1395 dispatches, 162 vs 39 ms, about 88 us per dispatch).
- It is NOT renderer-side encoding: the JS encode+submit of the replay is 0.5 ms (Chrome serialises commands to the GPU process; ORT's own run costs 43 ms of CPU but the frame time is unchanged at 142 ms with replay off, so CPU is not the limit either way).
- What this cannot separate: Dawn/Metal encoding in the GPU process and Metal inter-dispatch barrier/idle gaps both live inside those ~100 ms. Timestamps in the page are written in empty or padded passes, so they under-count by the same hidden gap. A direct test would be a single-pass or merged-pass replay (`replay.run({mergePasses:true})` exists but the page does not call it) or a hand-written engine.
- Verdict: hypothesis holds in the sense that frame time is about 4x shader time and tracks dispatch count, not shader work; it is unproven whether the cost is Dawn/driver per-dispatch overhead or GPU gaps. A ~60-dispatch fused engine should land near the 33 ms timestamp figure or better, not the 142 ms wall figure, if the overhead is per dispatch (about 1825 / 60 = 30x fewer).
