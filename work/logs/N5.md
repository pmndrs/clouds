# N5 log

## N5.1: dispatch-overhead probe (M5 Pro, Chrome headless, real GPU)

Page `examples/lab/neural-probe/` (plain WebGPU). Chain of dependent compute dispatches over 3 ping-pong storage buffers of 262,144 f32 (4,096 workgroups of 64 each), one pipeline object and one bind group per step, `setPipeline` + `setBindGroup` + `dispatchWorkgroups` each. Wall = before encode to `await queue.onSubmittedWorkDone()`, median of 20 after 5 warm-ups; encode = until `submit` returns. Timer resolution in Chrome is 0.1 ms. Work per dispatch is a serial FMA loop with a runtime trip count (first attempt used a constant trip count and the 1,825 case ran 4x faster than the 82 case, so the compiler treated them differently; the table below is after the fix). Runs: 1,825 dispatches x 32 iterations vs 82 dispatches x 712 iterations (same total).

| case | dispatches | passes | wall ms | ms per dispatch | encode ms |
|---|---|---|---|---|---|
| a: 1,825, work | 1,825 | 1 | 36.4 | 0.0199 | 0.1 |
| b: 82, same total work | 82 | 1 | 31.1 | 0.379 | 0.0 |
| c: 1,825, near-empty | 1,825 | 1 | 12.3 | 0.0067 | 0.1 |
| d: 82, near-empty | 82 | 1 | 0.8 | 0.0098 | 0.0 |
| e: 1,825, work, ORT-like passes | 1,825 | 276 | 36.5 | 0.0200 | 0.2 |
| f: 82, work, one pass each | 82 | 82 | 31.3 | 0.382 | 0.1 |

- Fixed per-dispatch cost is small: about 6.5 us (c minus d: 11.5 ms over 1,743 extra dispatches; this still includes launching 4,096 trivial workgroups, so it is an upper bound). 1,825 dispatches therefore cost about 12 ms of fixed overhead, 82 cost under 1 ms.
- Splitting into 276 passes (e) costs nothing measurable (36.5 vs 36.4 ms). Pass count is not the cause.
- Same total arithmetic in 82 dispatches takes 31 ms versus 36 ms in 1,825: a saving of about 5 ms, not 100 ms. ORT's 135 ms wall for 33 ms of shader time is NOT reproduced by dependent small dispatches, one pipeline and bind group each: this probe's equivalent of the 1,825-dispatch network is about 36 ms wall with the arithmetic included.
- So 82 fused dispatches of the same work would give roughly the GPU shader time plus ~1 ms, i.e. about 30-35 ms for the network at 512². The missing ~100 ms in ORT is not plain dispatch count. Candidates the probe does not test: ORT's real kernels (many bind-group buffer bindings, uniform buffer writes, different workgroup shapes), buffer-pool allocation or barriers between its passes, tensor readbacks or copies in the graph, and GPU idle gaps tied to its timestamp-query pass structure.

What the probe cannot tell: it is synthetic (one read and one write buffer, trivial layout, 3 buffers, no uniforms, no per-dispatch buffer writes, no copies, no real memory pressure from 1,151,649 weights and large activations). It shows only that Dawn/Metal on this machine does not impose ~55 us per dependent dispatch; it does not show where ORT's time goes. The consequence for ENGINE.md section 8: the planned 25-45 ms is not supported by a dispatch-count argument alone; it rests on the kernel throughput estimate. Task 10's timing of the real engine is the real test.

Raw: run via the page's `window.__clouds.report()`; reproduce with a local `npx vite` and `/neural-probe/`.

## N5.3: kernel throughput probe (M5 Pro, Chrome headless, real GPU)

Probe: Denoiser branch `claude/webgpu-neural-clouds-94935c`, commit `cf25beb`, `examples/wgsl-bench/halo.html` (`src/halo.ts`; run with `vite --config examples/wgsl-bench/vite.halo.config.ts --port 5197`, then `WGSL_BENCH_URL=http://localhost:5197/ node examples/wgsl-bench/run-headless.mjs "halo.html?precision=fp16&size=512&batch=6,4"`). It runs the Denoiser's fused 3×3 conv kernel (`conv.ts`, unchanged, default tiling 2×2 px × 8 ch per thread, 8×8 workgroups, f16 sums for fp16, no subgroup matrix) on HaloRT's 71 conv3×3 layers with random weights. Batch is a real batch (one dispatch per layer, workgroups along z = batch × channel groups), not repeated runs. Wall = encode to `queue.onSubmittedWorkDone()`; timestamps = one pass per layer, summed. Median of 20 after 5 warm-ups. GPU was idle before the run (IOAccelerator 0 %).

Approximations: the kernel's relu6 epilogue stands in for RMSNorm + SiLU; 1×1 convs, attention, pixel-unshuffle and residual adds are left out; all six batch items use one weight set; layers read and write scratch buffers, not each other's outputs (same shapes and sizes). The up-path concat convs use the kernel's two-source read (c1 + c2), the upsample convs its nearest-2× read.

### Estimate for the full network (*guess* above the measured conv line)

Not measured: 22 conv1×1 (0.6 GMAC per pass), 67 RMSNorm + SiLU, 5 block attentions, pixel-unshuffle, residual adds. Guess, fp16 512² batch 6: 1×1 convs 2–4 ms (memory-bound at level 0), norm + SiLU fused into the conv epilogue 2–5 ms (the norm needs all 16 channels of a pixel in one thread or a subgroup reduction; the one tiling that keeps all 16 cost +2.4 ms) or about 10 ms if run as separate passes, attention 1–3 ms, glue about 1 ms. Covered by the measurement: 94.8 % of the MACs, and by this guess about 60–75 % of the time.

ENGINE.md §8's range (25–45 ms at 512², 7–12 ms at 256²) holds, now on measured kernel throughput instead of the dispatch argument.

- A hand-written engine is worth building: the existing Denoiser conv kernel runs HaloRT's 3×3 convs (95 % of the work) in 19 ms fp16 at 512² for 6 passes, against ONNX Runtime's 135 ms for the whole network.
- Expected gain is about 4–5× at 512² (25–35 ms fp16 vs 135), and 256² with 4 passes lands near 7–9 ms, inside a real-time budget.
- Full resolution dominates: 77.5 % of the MACs and 70 % of the measured conv time, mostly the 16 → 16 and 32 → 16 convs; low-res levels cost little in absolute terms.
- The biggest unknown left is RMSNorm + SiLU: fused into the conv epilogue it adds a few ms, as separate passes about 10 ms at 512²; the engine should fuse it.
- fp16 is worth 1.5× over fp32 here (19 vs 29 ms); subgroup matrix was not tried (ENGINE.md expects nothing for fp16).
