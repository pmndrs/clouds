# N5.12: our engine on the live `/neural/` page

Date 2026-11-24. Check passed on the first try (fp32 and fp16). Code commit `9b1d9c2`.

## What changed

- `experiments/neural/halo-engine.ts` (new): `HaloEngine` = `haloNetGraph(HALO_GATHER_B6)` on `Engine` (batch 6,
  setSplit 3, weights `halo_dir.tza` + `halo_env.tza`), bound to `FeaturePass.packed`, plus a GPU blend op (one
  dispatch): `radiance[k] = (dir_k·light[k] + envScale[k]·env_k)·S + bg[k]·envScale[k]·(1 − S)`, S = packed 13,
  bg = 14–16. It writes `HaloNet.output` ([3,S,S] f32, rdv order), the buffer ONNX Runtime writes, so
  accumulate + tone map + display are the same code for both networks. 89 dispatches (88 network + blend), two submits.
- `experiments/neural/engine/runtime.ts` (additive): `Binding.buffer(id)` returns a tensor's slot buffer.
- `experiments/neural/halort-net.ts`: the accumulate step is now a public `accumulate()` that `run()` calls
  (behaviour unchanged).
- `examples/lab/neural/main.ts`: Review row **network: ONNX Runtime | our engine** (a select); `?net=engine|onnx`
  for captures. Default: our engine if it initialises, else ONNX (the option is disabled, error in its tooltip and
  in `report().engineError`). Precision follows the page's existing `?precision=fp16` for both networks (the engine
  converts the fp32 .tza to f16 itself, as the N5.10 page does). Status line names the network. Report adds
  `network`, `engineLoadMs`, `engineError`, `engineDispatches`. Page tools: `__neuralRadiance()` (+
  `__neuralRadianceChunk(k)`, 1 MB of base64 per call) and `__neuralTiming(runs)`.

## Input boundary (no gather pass needed)

The engine's first conv already gathers its 8 channels per batch item from a planar [17,H,W] f32 buffer (the
N5.10 fixture `cond` had exactly the layout of `packed`), so `packed` is bound as the engine input as is; no
extra compute pass, no readback. The 180° turn: `packed` is written in rdv order by the feature pass (N2b/N3a), the
network output and the blend stay in rdv order, and `HaloNet`'s display turns it back, as for ONNX. Nothing new.
The engine's output tensor is [6][1][S][S] in NC4HW4 (one vec4 per pixel, value in .x); the blend reads element
`(b·S² + i)·4` (f32) or the low half of u32 `(b·S² + i)·2` (f16).

## Odd

- **fp32 on this page is ~3× slower than N5.10's network-only number** (36 ms there; ~95–103 ms here with
  features, and widely spread, min ~62). fp16 here is 33 ms total, so the feature pass is small (≤ ~10 ms) and the
  fp32 network itself is slow on this page. Guesses, not tested: memory pressure from ORT's fp32 512 session and
  our fp32 slots (100 MB per level-0 slot) on one device, or the rAF display loop interleaving. Not tuned (rule 5);
  worth a look in N5.11 / N7 (e.g. time with ORT not loaded).
- Capture gotcha: with `CLOUDS_NO_WATCH=1`, vite keeps serving the first transformed module after an edit; restart
  the server after changing page code. Large CDP returns (4 MB) time out in `capture.mjs`; hence the chunks.
- The engine path still needs ORT loaded (HaloNet owns the output/accum/display buffers); if the ORT CDN import
  fails, the page fails as before.

## For batch 4 and 256² network with 512² features

- Batch 4 (N7.1, grey albedo, setSplit 1): the blend hard-codes items 0–2 = dir R,G,B and 3–5 = env R,G,B. With
  1 dir + 3 env, it must read dir from item 0 for all three colours and env from items 1–3; the gather table
  changes too (`HALO_GATHER_B6` → a 4-row table). Small change to `blendWgsl` (a batch/layout flag).
- 256² network with 512² features (N7.2): the engine reads `packed` at its bound size, planar with plane = size²,
  so a 512² `packed` cannot be bound to a 256² engine directly; it needs a downsample pass into a 256² [17,…]
  buffer (or the feature pass run at 256²). The blend's S and background would then come from either the 256²
  buffer (then upscale the radiance) or the 512² one (upscale the network outputs first). The blend assumes one
  plane size for both `cond` and the network output today.
