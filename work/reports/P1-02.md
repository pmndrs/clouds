## API
- `atmosphereWgsl(group)` declares bindings 0 uniform `Atmosphere`, 1 transmittance LUT, 2 sky-view LUT, 3 AP LUT (3D), 4 linear clamp sampler, and defines:
  `sunRadianceAt(p)`, `skyAmbient(p) -> {upper, lower}`, `applyAerialPerspective(color, T, viewDir, distance)`, `applyAerialPerspectiveUv(color, T, uv, distance)`, plus `atmAerialPerspectiveAt(uv, dist) -> (inscatter, 1-T)` and `atmTransmittanceToSun(p)`.
- TS in the same file (no three): `ATMOSPHERE_UNIFORM_FLOATS` (36), `writeAtmosphereUniforms`, `createAtmosphereBindGroupLayout/Sampler/BindGroup`. Not yet exported from `packages/runtime/src/index.ts` (orchestrator-owned): add `export * from './shaders/atmosphere.wgsl'`. The bridge and test import by relative path.
- `createSkyBridge(renderer, sky, {planetCenter?})` (three): `.update(camera)` after `sky.update(camera)` writes the uniform with no allocation (`writeBuffer` of a preallocated array); `.bindGroup`, `.layout`; `.rebind()` after a LUT resize.
- Units: `sunRadianceAt` is illuminance in the sky's exposure (`luminanceScale * T * sunColor`), the number three's light uses. `skyAmbient` is the cosine-weighted mean radiance per hemisphere (irradiance / pi), same scale. Both include `luminanceScale` and `sunColor`. Multiply by pi for irradiance.
- Frame: flat (the sky's default: altitude = world y, up = +Y, planet centre is implied) or planet mode (`planetCenter` in world metres, up radial). Radii are km inside the LUT maths, world is metres.
- Sunset: below the planet horizon at that altitude `sunRadianceAt` is 0 (same rule as the sky's CPU twin). The light's flat-world disc fade (`horizonFade`, sun within 0.27 deg of the horizon) is not applied; the test skips sun elevation below 2 deg.

## LUT mappings (sky source: /Users/dex/Developer/SebH-TSL-Sky, `git` HEAD is just past 0.5.0; the grade commit did not touch these)
All LUTs store values per unit sun illuminance (CLAUDE.md "LUTs use ILLUMINANCE_IS_ONE"); the consumer multiplies by `luminanceScale` (`SkyAtmosphereMesh.ts:344`, default 40, set by `sky.setExposure`) and `sunColor` (`SkyAtmosphereMesh.ts:377`, mesh applies it at :617). Sun light: `SkySun.ts:410-418` = `luminanceScale * T(sun)`.
- Transmittance LUT, 256x64 (`core/resolutions.ts:19`), rgba16f. Forward map `transmittanceLutParamsToUv`, `core/wgsl/atmosphere.wgsl.ts:377-390`: `H=sqrt(top^2-bot^2)`, `rho=sqrt(r^2-bot^2)`, `d = -r*mu + sqrt(r^2(mu^2-1)+top^2)`, `uv = ((d-dMin)/(dMax-dMin), rho/H)` with `dMin=top-r`, `dMax=rho+H`. Inverse `:352-375`. No sub-UV correction (readers use the raw uv, `luts.wgsl.ts:271`). r in km (6360..6460), mu = dot(sun, local up). CPU twin with the same maths: `core/sunTransmittance.ts:32-85`.
- Sky-view LUT, 192x108 (`resolutions.ts:20`). Forward map `skyViewLutParamsToUv`, `atmosphere.wgsl.ts:237-266`: `beta=acos(sqrt(h^2-bot^2)/h)`, `zenithHorizonAngle=pi-beta`; sky branch `v=(1-sqrt(1-acos(vz)/zha))/2`; ground branch (ray hits planet, `vz < -sqrt(1-(bot/h)^2)`) `v=sqrt((acos(vz)-zha)/beta)/2+0.5`; `u=sqrt((1-lightViewCos)/2)`; then `fromUnitToSubUvs(x,res)=(x+0.5/res)*res/(res+1)` (`:64-68`) on both axes with the LUT's own size. Inverse `:201-232`. `lightViewCos` is the cosine of the azimuth between the view ray and the sun in the plane perpendicular to up (`atmosphere.tsl.ts:722-733`); `vz` is dot(view, up). Baked for the camera: height `h` = `skyViewLUT.viewHeight` (set in `SkyAtmosphereBaker.ts:384/390`), up = `baker.cameraUp`, sun zenith = dot(sun, up) (`_syncSkyViewSunFrame`). Radiance is camera-centred: it is exact only at the camera's altitude and up (flat mode: everywhere in the horizontal plane).
- AP LUT, 32x32x32 rgba16f, 8 km/slice (`resolutions.ts:22`). Built in `sky/luts/AerialPerspectiveLUT.ts:266-283`: x,y = texel centres in ndc, **row 0 = ndc.y +1** (v down); z slice `w=(z+0.5)/32`, path `tMax = w^2 * 32 * 8 km`, so the sampling coordinate is `w = sqrt(distKm / (8*32))` (`HazePostProcess.ts:402-403`), clamped to 1 (256 km). Distance is along the ray, not view z. rgb = in-scatter per unit illuminance, a = 1 - mean(T) (`AerialPerspectiveLUT.ts` alpha line). Composite as the haze does, `HazePostProcess.ts:632,806`: `scene*(1-a) + rgb*luminanceScale*sunColor`. Needs `sky.updateAerialPerspective()` once per frame (async compute, ~0.3 ms) and the AP camera's matrices (`AerialPerspectiveLUT.setCamera`); my WGSL maps a world direction to uv with `projection * view-without-translation`.
- Planet radius 6360 km, top 6460 km (`AtmosphereParams.ts` EARTH). Flat convention `viewHeightKm = bottom + camera.y*0.001` (`SkyAtmosphereBaker.ts:390`); planet mode `|camera - planetCenter|*0.001` (:384).

## Findings
- AP at a ground camera looking exactly at the horizon under-reads: the texel rows straddling the horizon point below it, where the underground-froxel correction (`AerialPerspectiveLUT.ts:296-320`, `PLANET_RADIUS_OFFSET` 10 m, camera at 1 m) shortens the path, so the centre ray reads about half the true attenuation beyond ~10 km. Clouds sit above the horizon so this does not affect them; the test probes a ray pitched 4 deg up.
- `skyAmbient` integrates in the LUT's own (u, v) space (8 v-nodes x 8 azimuths per hemisphere = 128 taps). Midpoint rings uniform in sin^2(zenith) read 5-15 % low because they miss the bright horizon band. Evaluate it once per frame, not per pixel; the P1-05 march should read a per-frame value.
- The cube/PMREM are not needed for cloud lighting; only the three LUTs and the sun are.

## Investigation: why animating time of day costs "10-11 ms" (no sky changes made)
Setup: `runtime-tests/atmosphere/sky-cost.html`, flagship's sky config, 1280x720, three r186 (`pmrem mode sky, layout atlas`), M-series Mac. Every frame the sun moves, so the sky re-bakes: sky-view LUT render, 6-face cube capture (256), PMREM compute (`SkyAtmosphereBaker.ts:836,856,865`).
Two measurements: three's `render` timestamp (what the flagship HUD calls `scene`), and wall clock per frame (submit then `queue.onSubmittedWorkDone`).

| Scenario | three render ts (ms) | wall ms/frame |
| --- | --- | --- |
| sun fixed | 0.6 | 0.57 |
| animate every frame, defaults | 11.9 | 2.35 |
| only sky-view LUT re-render | 1.8 | 1.08 |
| only cube capture | 1.0 | 1.06 |
| only PMREM prefilter | 10.1 | 2.08 |
| pmrem quality fast | 10.1 | 1.95 |
| pmrem `generator:'three'` 250 ms / 1000 ms | 4.8 / 2.6 | 1.41 / 1.40 |
| cubeSize 64 / 128 / 512 | 5.9 / 7.3 / 11.9 | 1.55 / 2.14 / 4.05 |
| quality low (smaller LUTs) | 7.8 | 1.94 |
| cubeSize 64 + pmrem fast | 5.8 | 2.17 |
| update every 4th / 15th frame | 3.4 / 1.4 | 1.18 / 1.06 |
| every 4th frame + cubeSize 128 | 2.2 | 1.22 |

Isolated ops by wall clock: sky-view LUT 0.5-0.7 ms, cube capture 0.5-0.9 ms, PMREM prefilter 1.3-1.8 ms, AP compute 0.27 ms, a whole frame with the sun moving 1.7 ms vs 0.35 ms fixed.
Conclusions:
- The real cost of moving the sun every frame is about 1.8 ms (2.35 vs 0.57 ms/frame), almost all PMREM plus about 0.5 ms each for the LUT and the cube. The 10-12 ms in three's `render` timestamp is an attribution artefact: PMREM runs as raw compute outside three, and the timestamp of the next three render pass absorbs it (the "only PMREM" row reads 10.1 ms ts with no PMREM in three at all, and it scales with cube size). The frame rate was never affected (P0-03: p50 16.7 ms), consistent with 2 ms. Budget the cloud passes with their own `GpuTimer` numbers and treat `scene` with `animateTime` on as unreliable.
- Cheapest reductions, in order: update cadence (setting the time every 4th frame costs 0.6 ms real, invisible at 0.5 h/s; every 15th frame costs 0.5 ms), `pmrem: { generator: 'three' }` (1.4 ms, spreads the work over frames), `cubeSize: 128` (2.1 vs 2.35, small) . `pmrem.quality: 'fast'` and `quality: 'low'` save little. There is no option to skip the cube/PMREM bake; if the cloud flagship never uses `scene.environment`, a sky option to skip the cube + PMREM would remove about 1.5 of the 1.8 ms (a request to the sky author, not done here).
